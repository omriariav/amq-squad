amq-squad

amq-squad 3.0 runs a squad of coding agents (Claude Code, Codex and the built-in pi) on one repository, inside grants the owner sets, over durable AMQ by Aviv Sinai. It is a rebuild on AMQ's coop primitives: the v2 launch and orchestration code is gone, and what remains is a smaller, security-first core.

The model in five lines:

  • AMQ is the rail. Seats start through AMQ's launch API; mail, wake and cross-project routing are AMQ's.
  • The squad is one file. <repo root>/squad.yaml names the seats, the lead and the narrowing of the owner's grant. It is written only through a digest the owner (manual mode) or the grant (auto mode) approves.
  • The owner's limits live outside the repository. ~/.amq-squad/grants.yaml sets the mode, the seat and cost caps, the runtimes and the merge grants; squad.yaml can only narrow it.
  • Seats never commit, merge or release. A seat edits its worktree; the harness commit step commits only the task's declared files, the merge train lands PRs inside the merge grant, and tags and releases wait for the owner.
  • Four typed gates stop for the owner: tag and release, external send, credential change, and growth beyond the grant. The owner answers from Buzz on the phone with a signature the Go core verifies.

What's new in 3.0

Everything: docs/v3.0.0-release-notes.md lists the release by phase. In short:

  • squad.yaml schema 1 replaces the v2 profile, through team propose and team apply (docs/squad-yaml.md).
  • A task store with leases and pools, and a scheduler process beside the lead.
  • seat-exec in front of every seat: a scrubbed environment, the identity from the launch record, a read-only identity proof.
  • The harness commit step, the merge train under the standing merge grant, and the release flow behind the tag and github_release gates.
  • A runtime registry with the owner's pins, re-hashed at every launch.
  • The Claude Code hooks plugin (docs/claude-hooks.md), the built-in pi package, and the Buzz attachment on amq-remote's mailbox adapter.
  • amq-squad migrate for v2 profiles and amq-squad uninstall (docs/uninstall.md).

Install

go install github.com/omriariav/amq-squad/v3/cmd/amq-squad@v3.0.0
amq-squad version

The module path carries /v3. A go install build has no embedded pi runtime: amq-squad lead, solo mode and pi seats refuse with "this amq-squad build carries no pi runtime". The pi runtime is embedded only by a darwin arm64 build from a checkout, with scripts/build-pi-runtime.sh all (one networked fetch of Node, fd and rg with checked SHA-256s, then an offline go build -tags amqpi to build/pi/amq-squad). Claude and Codex seats need no pi runtime.

The Claude Code plugin carries the skills and the seat hooks. Install it at user scope (docs/claude-hooks.md):

claude plugin marketplace add omriariav/amq-squad --scope user
claude plugin install amq-squad@amq-squad --scope user

For Codex, add the same marketplace with codex plugin marketplace add omriariav/amq-squad. The skills (amq-squad:wizard, amq-squad:cli, amq-squad:orchestrator) are described in docs/skills.md.

Requirements

amq-squad doctor probes all of these and names what is missing:

  • amq 0.116.2 or later on PATH (and amq-remote, amq-owner-sign at the same release when installed); amq-squad doctor refuses an older one
  • Claude Code (claude) for Claude seats, with the owner's pin and token file (below)
  • Codex (codex) for Codex seats, with each seat repository trusted in ~/.codex/config.toml
  • the built-in pi (a pi-runtime build, above) for the pi lead and pi seats; ollama for local pi models
  • tmux: AMQ creates each seat as a tmux pane
  • gh, pinned in the registry, for the harness's PRs and HTTPS pushes
  • macOS on Apple silicon (see "Platforms" below); Go 1.25+ to build
  • pandoc 3.11 only to regenerate or check README.html and docs/skills.html

AMQ 0.116.2 is the minimum supported release: it is the AMQ module 3.0 links, and every 3.0 path needs its launch adapters (pi seats through the pi adapter, the Codex sandbox pins in the launch request) and its mailbox. amq-squad doctor refuses an installed amq, amq-remote or amq-owner-sign below it and prints the upgrade line (amq upgrade --all -y, or brew upgrade avivsinai/tap/amq). CI runs the real-AMQ lane at the pinned v0.116.2, which is required, and at latest as a non-blocking canary; a canary failure reads as upstream drift, not as a support claim.

Platforms

3.0 supports macOS on Apple silicon. On Linux the binary builds and the Claude hook script is tested, but seats are not supported in 3.0, for two reasons found on the first Linux test run. First, the launch's proof socket fails under a long project path (the Unix socket path bound). Second, ext4 and tmpfs reuse an inode right after an unlink and recreate, so the device-and-inode identity checks the harness uses against replacement of its seed, its sockets and its anchored directories are weaker there than on APFS, which never reuses one. Linux seats are 3.1 work.

First run

Each step below is the owner's, at the owner's own terminal. amq-squad never writes the owner's Claude or Codex configuration and never answers a trust prompt for you.

1. The AMQ root. The repository needs an AMQ queue first: run amq coop init once inside it (AMQ's verb; it writes .amqrc and .agent-mail/).

2. Probe the host. doctor checks AMQ and its launch API, the tools and their logins, the registry, the pins, the token file, the grants file, the Codex trust rows and the owner's global agent config. It writes nothing unless asked:

amq-squad doctor
amq-squad doctor --project .
amq-squad doctor --json

3. The registry. amq-squad doctor --write-registry writes ~/.amq-squad/registry.yaml: one entry per runtime, model and effort it detected. The lead proposes seats from verified entries only.

4. The pins. Seats never run a tool from PATH. The registry's pins: list names each harness tool by absolute path and sha256, and every launch re-hashes it (tool_unpinned or tool_pin_mismatch refuse the launch):

  • claude: a hard link named claude to the versioned Claude Code binary on the same filesystem (a symlink is refused), for example ln ~/.local/share/claude/versions/<version> ~/.amq-squad/bin/claude, then its path and shasum -a 256 in the pin. Re-pin after every Claude Code update. Without it a launch with a Claude seat is refused.
  • gh: the same for gh, needed for an HTTPS push target. doctor's gh pin row prints the exact entry to add.
pins:
  - name: claude
    path: /Users/you/.amq-squad/bin/claude
    sha256: <64 hex>
  - name: gh
    path: /opt/homebrew/bin/gh
    sha256: <64 hex>

5. The token file. Claude seats authenticate with a long-lived token, not your login: run claude setup-token and save the token it prints, alone, to ~/.amq-squad/claude-token with mode 0600. A missing or loosely-permissioned file refuses Claude seats (claude_token_insecure). Never paste the token into a command line.

6. The grants file. ~/.amq-squad/grants.yaml (strict YAML subset, mode 0600; a group- or world-writable file fails closed to manual mode with no merge grant). Without it the built-in defaults apply: auto mode, 12 seats per session, no merge grant. A small example:

schema: 1
mode: manual
max_seats: 6
permitted_runtimes: [claude, codex, pi]
merge:
  - repository: you/app
    base_branch: main
    ci_required: true
    size_cap_lines: 400

The keys a squad can narrow, and the ones it can never set, are listed in docs/squad-yaml.md.

7. Codex trust. A fresh Codex seat stops on its folder-trust prompt. This prints the lines you add to ~/.codex/config.toml yourself, and the candidate Codex notify fan-out line:

amq-squad trust .

8. The squad. team propose prints every file the squad needs (squad.yaml, .amq-squad/team-rules.md, the CLAUDE.md and AGENTS.md pointer stubs) with one digest, and writes nothing. team apply with that digest and the same options writes them; a changed option (squad_yaml_digest_mismatch) or a hand edit in between (squad_yaml_changed) writes nothing:

amq-squad roles
amq-squad team propose --project . --roles cto,fullstack,qa --runtime fullstack=codex --worktree fullstack=../app-96 --lead cto --session issue-96
amq-squad team apply --digest <digest> --project . --roles cto,fullstack,qa --runtime fullstack=codex --worktree fullstack=../app-96 --lead cto --session issue-96
amq-squad team show --project .
amq-squad team check --project .

A per-seat flag takes one comma list: --worktree a=x,b=y, never the flag twice (a repeated per-seat flag is refused). A custom role is staged first with amq-squad role draft researcher --purpose "Investigate ambiguous behavior".

9. The brief. The workstream's goal, at .amq-squad/briefs/<session>.md:

amq-squad brief --goal "fix issue 96" --session issue-96 --dry-run
amq-squad brief --seed-from file:./prompt.md --session issue-96

10. Launch. Three entry points, each one AMQ launch request with every seat behind seat-exec:

  • amq-squad launch --seats seats.json: the typed seat list (JSON; the format is in amq-squad launch --help). A required action such as AMQ's trust confirmation stops the launch with exit 10 and is never answered for you.

  • the pi lead in team mode with the scheduler beside it; the lead never edits code, it dispatches through the task store, and the scheduler starts seats on demand:

    amq-squad lead --team --scheduler-seats seats.json --dry-run

    (drop --dry-run to start it; a pi-runtime build only).

  • the mayor inside the owner's fleet grant: operator start-squad writes the squad.yaml through the same digest flow and launches it; in manual mode it returns a proposal instead.

amq-squad launch --seats seats.json --dry-run

In a directory with no AMQ identity, amq-squad lead (or a bare amq-squad on a terminal) starts the pi lead in solo mode: its state lives under ~/.amq-squad/solo/, nothing is written in the repository.

Running a squad

The lead's loop is one status read, one bounded action, then park; AMQ wake delivers the next message. amq-squad:orchestrator is the lead's playbook.

amq-squad status --project . --session issue-96 --json
amq-squad task add --title "Fix the parser" --class implement --files internal/parse/ --pool claude:sonnet:medium --project . --session issue-96
amq-squad task list --project . --session issue-96
amq-squad gate status --project . --session issue-96 --json
  • Status is the versioned contract of docs/status-contract.md: four buckets (Needs you, Working, Ready, Inactive), seats, tasks, the attention queue and gates, with argv actions. amq-noc renders it for the fleet; amq-squad status --fleet --json reads every squad of ~/.amq-squad/fleet.yaml.
  • The commit step. On a seat's done report the scheduler runs seat commit: every changed path against the task's declared files, the protected paths and the size cap, then a commit under the harness identity and a fast-forward push of the seat branch. A path outside the set comes back to the lead, whose decision is task widen ID --files ... --reason ... (no --me: the scheduler proves the lead from the process).
  • Merge. merge-train --request FILE --dry-run plans and checks the lead's ordered PR set against the merge grant; the real run uses the owner's gh, outside any seat. Seats never merge.
  • Release. release prepare raises the tag and github_release gates; release publish runs each only with its verified owner answer.
  • Quarantine. A seat that changed the owner's global agent config is quarantined; only the owner clears it, with seat clear from the owner's own terminal.

Check whether an action is approved, and the evidence of a merge or a release:

amq-squad verify action --project . --session issue-96 --gate rel-v3 --action tag --target "git tag v3.0.0" --json
# skill-invocation-check:skip — exits 1 ("merge evidence failed") where no merge-train run is recorded, by design
amq-squad verify merge --repository you/app --pr 12 --root /path/to/app/.agent-mail/issue-96 --json
# skill-invocation-check:skip — exits 1 ("release evidence failed") where no release flow is recorded, by design
amq-squad verify release --tag v3.0.0 --root /path/to/app/.agent-mail/issue-96 --json

verify action exits 0 approved, 10 pending, 11 denied, 12 no gate, 13 unbound.

The owner's Buzz face

One Buzz agent, the body of one amq-remote share, attaches to the operator session's mailbox (or with --lead to one squad lead). The owner's guide is docs/v3-buzz/README.md.

  • Enrollment is the owner script docs/v3-buzz/enroll.sh <owner-npub> <relay-url>, run once per 30-day grant window. The Buzz key reaches amq-owner-sign only through a password-manager pipe (BUZZ_OWNER_KEY_CMD); nothing in amq-squad, amq or amq-remote reads it. The script ends with remote bind, which writes the owner's gate binding ~/.amq-squad/gate-binding.json (no secret in it).
  • The mailbox adapter. amq-remote serve delivers each DM from the owner into the share's mailbox; remote attach answers each once (accepted, refused, routed), and serve posts the reply under the message. A message starting with @<lead> is routed to that squad lead.
  • The gates. A typed gate's question goes to the owner's DM with its reply thread; the owner answers in that thread, and the core of the squad that raised it fetches and verifies the signed event itself. An answer outside the thread is refused with one re-ask.

amq-squad remote status

Command map

amq-squad --help and each verb's --help are the reference. The verbs:

Area Verbs
Host and setup doctor, trust, roles, role draft, team propose/apply/show/check/draft-rules, brief, migrate, uninstall, version
Launch launch, lead, scheduler run, seat-exec (AMQ runs it), pi run/verify/path
Work task add/list/show/claim/renew/done/fail/block/release/reset/set/cancel/widen/reconcile, dispatch, seat commit, seat clear, worktree
Hook verbs context, guard, evidence ingest, evidence list
Gates and landing gate raise/answer/status/post/close, verify action/authorization/merge/release/release-plan/rebind, merge-train, release prepare/publish
Fleet and owner status, status --fleet, fleet list/add/remove/operator, operator inbox/answer/start-squad, remote bind/attach/status, routing report --week, amq env/route

Exit codes common to every verb: 0 success, 1 usage or user error, 2 system or runtime error, 3 partial success; a verb with more (launch 10, verify action 10 to 13, seat commit and task widen 15) lists them in its help.

What 3.0 does not do

These are the recorded limits of 3.0. The full list, with its reasoning, is in docs/v3-plan.md (section 7 for the security model, section 16.4 for the phase 5 items and the open acceptance rows):

  • Same-UID boundary. Seats run as the owner's user. A same-UID process can read the owner's gh token from the login keychain (guard denies the CLI reads and the scrub removes the variables, but neither is a wall), forge AMQ mail as the lead, forge hook reports, and in principle swap the pi runtime in the milliseconds between its re-hash and its exec. The ledgers are sealed so a forgery is detected and blocks, not prevented. A dedicated keychain or GitHub App token and a read-only runtime image move to 3.1.
  • Hooks are UX and evidence, not enforcement. Claude Code's PreToolUse hook fails open on a timeout or an error; enforcement is the commit step and the merge train. Codex, Grok Build and Cursor seats have no hooks.
  • One owner DM at a time. The mailbox adapter answers a second DM busy while one is open; wait for each result row.
  • No seats-file compiler. launch --seats and lead --scheduler-seats take a hand-written typed seat list; only the mayor's operator start-squad compiles squad.yaml into the launch itself.
  • The pi runtime is darwin arm64 only and is not in a go install build.
  • Open acceptance rows at the tag (plan 16.4): the Claude live rows wait on the owner's token file, the first real merge-train run on a harness-bound PR, the pi launch through amq launch on the installed AMQ, amq-noc 1.0, and the signed seat clear live row.
  • No v2 verb survives: init, start, plan, resume, down, wizard, goal, team init/sync and the pane drivers are gone, with no aliases.

Uninstall

amq-squad uninstall --project . --session issue-96

A dry run by default: it prints every path it would remove. --write removes the session state, the per-seat config dirs, the pinned tool copies and the worktrees it created; the owner files only with --owner-files, the sealed ledgers only with --purge. It prints the Claude plugin and Codex trust commands for you to run. See docs/uninstall.md.

Upgrading from v2

MIGRATION.md "Moving to 3.0" is the list. The converter is a dry run unless --write is given, never writes grants.yaml or registry.yaml (it writes grants.yaml.proposed beside them), and prints every v2 field it did not map:

# skill-invocation-check:skip — exits 1 (migrate_input_invalid) where no v2 profile exists, by design
amq-squad migrate .amq-squad/team.json
