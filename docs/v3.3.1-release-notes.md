# amq-squad v3.3.1-rc.1

These are the notes for 3.3.1-rc.1, a release candidate, built from
`release/v3.3`: 3.3.0 with one fix, #1033, picked from v3. It is
published as a prerelease, not as the latest release. The module path is
unchanged:

```sh
go install github.com/omriariav/amq-squad/v3/cmd/amq-squad@v3.3.1-rc.1
```

A `go install` build carries no embedded pi runtime. The binary the squad runs
is built from the tag by `scripts/build-pi-runtime.sh`, as the owner steps
below show. The earlier notes are
[docs/v3.3.0-release-notes.md](v3.3.0-release-notes.md) and the notes it links.

## Fixed

### A gate raised into a new session can be answered (3.3.0's known limit 7 lifted)

In 3.3.0, a gate raised as the first write into a new session could never be
answered: `gate raise` or `release prepare` took the session's squad identity
before the session's directory existed, the gate carried an identity no
answer could match, and your yes or no was refused (`no_squad_identity`).
The workaround was to create the session's directory first (`mkdir -p
<project>/.agent-mail/<session>`).

In 3.3.1 every command that raises a gate checks the request first, then
creates the session's directory, and only then takes its identity: `gate
raise`, `release prepare`, the merge train's gates, and the growth gate. A
gate raised into a new session is answered like any other. A refused raise
(a bad window, a release commit not on its branch) creates no session
directory. The `mkdir -p` step is no longer needed; it does no harm.

### The merge train finds a gate approved in a session it joined before the session existed

In 3.3.0, a merge train started before its session's directory existed kept
the identity it read at start, so a gate raised and approved there later was
never found, and the merge it should have opened stayed refused. In 3.3.1 the
train reads the session's identity each time it checks for an approved gate.
Two `release prepare` runs into one new session likewise agree on a gate
either of them raised.

### The growth gate raised without a transport can be answered

In 3.3.0, a growth gate (a seat's widen past its grant) raised while the
owner's transport was unavailable was written with no squad identity at all,
in any session, new or not. When the question was posted later, every answer
to it was refused ("raise it again"). 3.3.0's notes did not name this. In
3.3.1 the gate carries its session's identity on both paths, with or without
a transport.

### What these defects never did

All three failed closed: nothing an affected gate guarded ran. A gate raised
into a new session, or a growth gate raised without a transport, could not
be approved; the merge train's gate could be approved, but the train did not
find the approval and kept the merge refused. A gate is approved only when
the owner's signed answer passes the verifier, which refuses a gate whose
identity is not its session's, or that carries none; the merge train, the
release flow, the guard and `verify action` read only that approval.

## Known limits lifted

- 3.3.0 known limit 7 ("A gate raised as the first write into a new session
  cannot be answered (no_squad_identity); create the session root first").

## Upgrading from 3.3.0

3.3.1 does not repair a gate 3.3.0 already wrote. A gate id is written once,
so the same raise again finds the old record:
- a gate 3.3.0 raised as the first write into a new session still carries an
  identity no answer matches. For `gate raise`, raise it under 3.3.1 with a
  new `--gate` id. For `release prepare`, prepare again into a new session.
  The merge train asks again for a new head, or in a new session.
- a growth gate 3.3.0 wrote while the transport was unavailable carries no
  identity, in any session, so no answer to it is accepted. Its id comes from
  the task and what the widening crosses, so widening the task again finds
  the same gate, and `task reset` refuses a task that waits for the owner.
  The lead raises a new gate for the same target instead; a widening counts
  an approved gate of any id for its target:

  ```sh
  amq-squad gate status --gate <old gate id> --json      # copy its "target"
  amq-squad gate raise --gate <new id> --action spawn --target "<that target>" --me <lead>
  ```

  If the raise says the question was not sent (`question_sent: false`), post
  it once the transport is back: `amq-squad gate post --gate <new id>`. Use
  the old gate's `--project`, `--profile` and `--session` throughout.
  Approve the new gate on your phone, then widen the task again from the
  lead's pane (`/widen`, or `amq-squad task widen <task> --path <path>
  --reason <text>`); it goes back to the pool. Cancelling the task and adding
  it again also works, but the new task starts over.

## Rolling back

- Gates 3.3.1 raised into a new session are answered under 3.3.0 too: their
  identity is the one 3.3.0 computes for that session.

## Known limits

Known limits 8 and 9 were added to the 3.3.0 notes after the release; 10 is
new here. The tagged 3.3.0 notes list 1-7.

- 8. A seat able to write its own agent directory can still be treated as
  the lead for Buzz routing and `task show`; gate approvals are unaffected.
  Planned for 3.3.2.
- 9. For Claude and pi seats, the protected-path guard is best effort against
  shell commands: a seat may be able to write files the guard protects,
  including the owner's grant file (`~/.amq-squad/grants.yaml`). A Claude
  seat could also change two kinds of Claude Code configuration the guard
  does not protect: the MCP file, and the main checkout's settings files
  when the seat works in a separate worktree; the Claude-seat sandbox planned
  for 3.3.2 is to close that. Codex seats are held by an OS sandbox. Until
  this is fixed, run untrusted work on Codex seats.
- 10. The phone attach routes to a squad's lead only when that lead has a
  launch record. A lead started by `up` has none, so the attach leaves its
  squad out: a phone message that names the lead (`@cto …`) is not
  forwarded, and if no squad is left the attach does not start. A message
  that names no lead goes to the operator's mailbox, as designed. Gate
  answers are unaffected while the attach runs.
- cursor-agent and grok seats have neither the guard nor a sandbox.

## Owner and lead steps for 3.3.1-rc.1

Install by temporary name and rename, from the tag, never from the working
tree (R54).

1. After the v3.3.1-rc.1 tag is published, build the tag in a scratch
   worktree:

   ```sh
   git worktree add ~/scratch-v331rc1-build v3.3.1-rc.1 && cd ~/scratch-v331rc1-build && scripts/build-pi-runtime.sh all
   ```

   The binary is `build/pi/amq-squad`.
2. Keep a copy of the installed binary first, so a rollback has it:

   ```sh
   mkdir -p ~/amq-squad-backup && cp -p ~/go/bin/amq-squad ~/amq-squad-backup/ && shasum -a 256 ~/amq-squad-backup/amq-squad
   ```
3. From the repository, run `up` from the tag build:

   ```sh
   cd ~/code/amq-squad
   ~/scratch-v331rc1-build/build/pi/amq-squad up --binary ~/scratch-v331rc1-build/build/pi/amq-squad
   ```

   If the squad's lead is running, quit it first: `up` installs the binary
   and then refuses `lead_running`, because it never stops a lead whose tmux
   pane exists.
4. Read the lead's first screen and record it in the release evidence
   (RELEASING.md step 6). A dead pane or a `Failed to load extension` line
   means the release is not done.
5. Restart the phone attach with its usual command line, so it runs this
   build, and check that it logs `attached` and validates its squad. As in
   3.3.0, a squad whose lead has no launch record (a lead started by `up`)
   is left out, and an attach with no squad left does not start (known
   limit 10).
