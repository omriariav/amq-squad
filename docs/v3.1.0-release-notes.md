# amq-squad v3.1.0-rc.1

These are the notes for the 3.1.0 release candidate 1, built from the tip of
v3 after #832. The candidate is not the release: it exists so that the owner's
day-4 launch-budget run has a tagged binary, because `amq-squad up` refuses an
untagged build (R54). The notes grow into the 3.1.0 notes. The module path is
unchanged:

```sh
go install github.com/omriariav/amq-squad/v3/cmd/amq-squad@v3.1.0-rc.1
```

A `go install` build carries no embedded pi runtime. The binary the squad runs
is built from the tag by `scripts/build-pi-runtime.sh`, as the owner steps
below show. Upgrading from v2: see [MIGRATION.md](../MIGRATION.md). The earlier
notes are [docs/v3.0.2-release-notes.md](v3.0.2-release-notes.md),
[docs/v3.0.1-release-notes.md](v3.0.1-release-notes.md) and
[docs/v3.0.0-release-notes.md](v3.0.0-release-notes.md).

## What 3.1 is

3.1 is the release the owner redirected on 2026-10-31, after installing 3.0.2
and resuming the squad (docs/v3.1-plan.md, section 7). The owner said:

> "security is too much... we need to put the TUI and UX top. its should be
> easy to leverage AMQ by launching different binaries and models. i get the
> gates; it's the operator via the lead or via buzz. i think its safe enough."

and:

> "yes, launching binaries/models should be FAST! like claude agents teams. i
> want the next version either 3.0.x or 3.1 to focus on this"

Offered the choice between A, delete the launch-blocking guards, and B, keep
them as a strict profile for the release run, the owner answered "A". 3.1
therefore deletes the guards, makes squad.yaml the one source of a launch,
gives a launch a number, and puts a screen and its keys in the lead. The four
typed gates stay owner-signed over Buzz; the lead's screen shows them, and the
terminal door is not in this candidate. The standing merge grant is unchanged. The version is 3.1
because a seat that would have been quarantined now starts, a changed default
on a released line. 3.0.x stays fixes only.

3.1 is built by agents in scratch worktrees under the lead's briefs, each PR
with a Codex pass, the plan reviewer's read and the lead's gate. The items
below are the merged PRs of the two briefs and the redact fixes.

## The launch guards deleted, squad.yaml the one source, one lead per root (#828)

Brief 31-1, PR 1. The execution note is
[docs/v3-spike/31-evidence/31-1-launch-and-screen.md](v3-spike/31-evidence/31-1-launch-and-screen.md).

- A seat is no longer quarantined. A Claude seat whose hook made no report,
  whose worktree carries Claude allow rules, or whose CLAUDE.md imports a file
  outside its worktree starts, with a warning on its status row. A change to
  the owner's global agent config during a run is no longer a quarantine. A
  seat's write to `~/.claude/settings*.json`, `~/.claude/plugins/` or
  `~/.codex/config.toml` is still denied at tool time as `protected_path`.
- Deleted, each with the tests that pinned it: the hook probe as a quarantine
  reason; the config-drift preflight baseline and its diff; the task store's
  quarantine and the ledger's quarantine and signed clears; `seat clear`, the
  `quarantine_clear` gate kind and the `clear.signature` grant key; the Claude
  pin and the mode probe; the Claude config-dir refusals; the wake conditions
  as refusals; `--trust`; the hand-written seats file with `launch --seats`,
  `lead --team --scheduler-seats` and `--lead`; the empty-worktree exclusion;
  `codexModelLists` as a gate; the pi model refusal; and the launch's
  push-target refusal, which now runs only in the commit step. The note lists
  every deleted file with the caller search that shows it dead.
- The trust confirmation's answer is a constant every launch carries. A
  Codex seat's wake reads AMQ's dialog hook only, since a doorbell at an
  approval prompt cancels the pending command. A pi seat stays wake-off,
  because the embedded runtime does not carry AMQ's pi extension.
- The runtime lists are AMQ's five providers: claude, codex, cursor-agent,
  grok and pi. Grok passes model and effort, cursor-agent passes model only,
  and any other runtime is refused by name at parse. The router admits each
  roster seat's own pool without a registry entry or a table chain.
- squad.yaml is the one source. It carries each seat's handle, role, runtime,
  model and effort, and the lead handle and session. `lead --team` in a
  repository with a squad.yaml reads them and runs `scheduler run --project`.
  A seat's worktree is derived as `<repo>/.worktrees/<handle>`, and a
  squad.yaml worktree naming the repository root is a parse error. The
  checked-in squad.yaml launches.
- One lead per root. A second `lead --team` on the same root refuses
  `lead_running`, naming the first lead's pid and tmux pane, before its
  scheduler starts. A second scheduler exits 17, which the supervisor does not
  restart. A lead that exits non-zero stops its scheduler first.
- A ledger_tampered refusal at a seat's exit, the one quarantine producer that
  was not a config reason, closes the seat with the decision `exit_refused`
  and a notice to the lead. The commit step refuses the same ledger.
- With no gh pin on the launch record, the base-tip fetch is anonymous, with
  every credential helper off. A public repository launches. A failed
  anonymous fetch refuses `base_fetch_unauthenticated`, with the way out: pin
  gh for a private HTTPS repository, or use SSH.
- `lead --team` records the start stamp (`AMQ_SQUAD_START`) in the
  scheduler's `launch.json`. Nothing stamped the owner's start before.
- Compatibility: an old quarantine record in a live task store is no longer
  honored, so the seat it named starts on the next launch with nothing to
  clear. An old `clear.signature` key in grants.yaml loads, has no effect, and
  doctor's grants row warns with the key named. A `quarantine_clear` gate
  record already in a gate store is listed and skipped with one line, never a
  refusal.
- The baseline, from the last 2026-10-31 roster launch on 3.0.2 and measured
  from the scheduler's own start, since nothing stamped the owner's: dev 4.485
  s, reviewer 4.419 s and scribe 4.666 s to seat live. The reviewer's first
  message came at 57.449 s.

## `amq-squad up`, the status additions, the launch budget, the screen (#829)

Brief 31-1, PR 2. The execution note is
[docs/v3-spike/31-evidence/31-1-pr2-up-status-screen.md](v3-spike/31-evidence/31-1-pr2-up-status-screen.md).

- `amq-squad up` starts a repository's squad from squad.yaml in seven steps,
  in order, each refusing by name with nothing after it running: compile,
  install, session, doctor, lead, tmux and roster. `--json` prints each step.
  The install copies the tagged pi build to a temporary name beside the
  `amq-squad` on PATH and renames it over, never writing in place. The lead
  starts in its own tmux session, `squad-lead-<repo>-<sha5>`, with
  `AMQ_SQUAD_START` set. `up` waits for the roster decision and prints the
  roster with each seat's launch budget and the attach command.
- The missing-session refusal is deleted. `up` and `scheduler run` create the
  AMQ root and the session when absent, and log `session_created`.
- Against a recorded lead, `up` follows one rule. A live lead with its pane
  present refuses `lead_running` with the pid, the pane and the attach command,
  and stops nothing. `up` stops only a dead lead, a lead whose pane is gone,
  and a scheduler whose lead check has passed, by the recorded pid and start
  stamp, and records each stop as `up_stopped_lead` or `up_stopped_scheduler`.
  It kills only the `squad-lead-*` session it named, and never the tmux session
  of a lead started by hand.
- The launch budget has two marks per seat. Seat live is the accepted proof's
  stamp. The first message is the seat's first sent AMQ message, recorded once
  per launch as the scheduler decision `seat_first_message`. The ceiling of 10
  seconds binds the start to seat live. A seat over it carries
  `launch_budget_exceeded`, naming the slowest segment of prepare, mint, apply
  and seat-exec-with-proof. The first message has no ceiling until the day-4
  record sets one. Both marks and the segments are in status as
  `seats[].launch.timing`, on the screen's seat line and in `up`'s roster.
- Status grows additively under schema 1: the lead and the scheduler with
  their pids, the last 30 decisions, the merge train's runs and alerts, each
  seat's worktree, branch, launch outcome and admitted wake, each task's
  evidence and PR, and a file-lock wait's holders. Four seat warnings are new:
  `launch_budget_exceeded`, `wake_off`, `seat_stalled_at_dialog` and
  `pi_provider_key_missing`. Every free-text field passes the redactor before
  it is written. docs/status-contract.md describes the additions.
- The screen is a widget below the editor in the team lead's pi. Its first
  line is the lead handle and the root. Four blocks follow, seats, tasks,
  train and gates, each ending with its newest refusal or `none`. A warning is
  never shown as a refusal. The screen runs `status --json` only after
  `tasks/.generation` or `scheduler.json` changed. `/squad` collapses it to
  one footer line of counts. The screen reads and changes nothing.
- A file-lock wait names its holders, and a lock no task holds reads as stale.
  This came from the squad's own record: t26 sat four hours pending on a lock
  held, by the record, by two tasks already cancelled.
- `up` refuses by name, and the note records what each refusal leaves behind:
  `squad_invalid`, `pi_binary_untagged`, `pi_not_embedded`,
  `pi_runtime_rejected`, `pi_binary_missing`, `install_target_unknown`,
  `install_failed`, `amq_root_symlinked`, `decision_unrecorded`,
  `doctor_failed` or the failing row's kind, `up_running`, `lead_running`,
  `tmux_unavailable`, `lead_pane_unknown`, `lead_record_unreadable`,
  `scheduler_running`, `scheduler_unknown`, `lock_unsupported`,
  `roster_wait_timeout`, `roster_launch_failed`, `lead_exited` and
  `lead_gone`.
- Doctor runs after the AMQ root and session exist. On a fresh clone AMQ's
  `amq env` refuses a repository with no AMQ root, so the brief's order would
  have refused every fresh clone at doctor.

## The screen's keys: add, reset, clear, answer (#831)

Brief 31-2, PR 1. The execution note is
[docs/v3-spike/31-evidence/31-2-keys.md](v3-spike/31-evidence/31-2-keys.md).

- The keys are subcommands of the screen's `/squad` command: `/squad add`,
  `/squad reset`, `/squad clear` and `/squad answer`. pi runs a registered
  command in the extension and never sends its text to the model, so the model
  cannot press a key. Each key gathers its input with pi's dialogs and runs its
  verb from the lead's own process, so R4 holds by construction. A cancel at
  any dialog runs no verb. After a key the screen shows its outcome as one line
  at its foot and reads status again.
- add, for a task: `task add` with title, class, declared files and pool.
- reset: `task reset ID`, with `--pool` for a picked or typed pool. A re-pin
  refusal such as `repin_after_attempt` shows by name. A typed pool left empty
  aborts the key.
- clear: a fourth request kind on the scheduler's decision socket,
  `amq-squad.clear.v1`, sent by the new verb `scheduler clear --seat
  --warning --launch`. It acknowledges one seat warning for one launch. It is
  proved before and after it is read, like the widening and the relaunch, and
  from outside the lead's descent it is refused `not_lead`. It refuses
  `clear_not_a_warning` for a refusal code, `clear_launch_stale` when the seat
  has relaunched since the screen showed it, and `clear_not_showing` when
  status does not show that warning now. It records one line in `clears.jsonl`
  and one `warning_cleared` decision, and nothing else. Status lists the
  warning under `acknowledged_warnings` for that launch only, and a new launch
  brings the condition back.
- answer, and Q7: the brief asked whether an owner terminal key could sit in
  the macOS Keychain with user presence on every signature. The answer is no,
  from four facts. A user-presence key lives in the data protection keychain,
  which refuses an unsigned Go binary with error -34018. The entitlement-free
  CryptoKit path is Swift-only. The shipped binary is built with
  `CGO_ENABLED=0`. The `security` tool makes no suitable key and its prompt
  offers "Always Allow". Nothing is weakened to fit. The answer key is the
  written fallback: it reads the gate fresh, shows its kind, typed class,
  target and 16-hex prefix as Buzz does, posts the question with `gate post`
  only if it never reached Buzz, and says it is waiting on Buzz because the
  terminal door is not built. A gate that is not open refuses `gate_not_open`.
  The key never runs `gate answer`, which stays the verifier of the owner's
  Buzz reply. The gates block shows each open typed gate as waiting on Buzz.
- The lead's model tool list is exactly the thirteen tools of the tip. None
  names a key verb, a gate answer or a clear, and a test fails whenever a tool
  is added.

## The add key's seat half, the live roster reload, every relaunch stamping its own start (#832)

Brief 31-2, PR 2. The execution note is
[docs/v3-spike/31-evidence/31-2-pr2-seat-add.md](v3-spike/31-evidence/31-2-pr2-seat-add.md).

- A seat added to squad.yaml now starts at a roster relaunch. Before, the
  roster was compiled once at the scheduler's start, a relaunch relaunched the
  fixed roster, and the router admitted only the pools known at open.
- `/squad add` for a seat asks for handle, role, runtime, model and effort,
  then runs `team propose --add-seat HANDLE:ROLE:RUNTIME:MODEL:EFFORT` and
  `team apply --digest D --add-seat ...`, which re-render squad.yaml through
  the digest flow. It confirms once, with the line that this relaunches every
  seat, and then runs `scheduler relaunch --start STAMP` with the
  confirmation's moment. A propose refusal shows as `squad_invalid`, an apply
  refusal as `squad_yaml_changed` or `squad_yaml_digest_mismatch`, and a
  declined confirmation writes nothing.
- The reload is one step at the drain's end, or none. squad.yaml is compiled
  before anything drains, and a compile error refuses `squad_invalid` with the
  running roster untouched. After the drain the slots' squad, the router's
  pools and the roster are written in that order. A failure between writes
  undoes them, logs `roster_reload_failed` and relaunches the running roster
  unchanged. A success logs `roster_reloaded`, naming the added and removed
  seats. A squad.yaml that names another session or lead is refused, since both
  are the scheduler's for its life.
- The reload only adds. It stops no seat. A seat removed from squad.yaml keeps
  its lease through the drain, closes there with the reason `roster_relaunch`
  and is not launched again. A changed line for a live seat applies at that
  seat's launch. Until AMQ's ask 20 lands, the add key is a roster relaunch,
  so every live seat drains and comes back.
- Every relaunch stamps its own start, the relaunch decision's time, so a plain
  relaunch an hour after `up` shows no `launch_budget_exceeded` for that hour.
  A seat the reload added starts from the key press, the confirmation's moment,
  carried as `added_at` in its marks and shown in status as `launch.added_at`.
  The stamp is bounded: more than 5 seconds after the relaunch decision, or
  before the start of the launch running now, refuses `start_out_of_range`,
  and a malformed stamp refuses `relaunch_malformed`.
- The drain is a named segment. A relaunched seat's timing lists five
  segments, drain, prepare, mint, apply and seat_exec, so a busy squad's
  budget names the drain as the slowest rather than blaming seat-exec. A slow
  base-tip fetch counts as prepare, never as drain.
- The lease cap is recomputed at the swap from the grant read again at the
  drain's end. A squad past the cap launches every seat. The leases follow the
  cap, a seat beyond it waits `seat_cap`, and the scheduler logs
  `roster_over_cap`. The lead's screen shows one line, not a refusal.
  `team propose --add-seat` refuses a seat past squad.yaml's `max_seats`.
- Every runtime squad.yaml accepts has a launcher, so an added seat with a new
  runtime launches.
- The note records 38 revert runs, each failing its rows.

## The redact fixes (#827 and #830)

- #827, 3.1 task t2: the linearity row for `redact.Block` measures work units
  and allocated bytes, not wall-clock time. The old row failed twice on
  GitHub's runners on 2026-10-31, on docs-only PRs. The new row asserts at most
  24 times the work and 40 times the bytes for a 16 times larger input, and
  three mutations, a per-match copy, a prefix rescan and a head-search sort,
  each trip it. A quadratic loop that neither reports to the hook nor allocates
  still slips through, and the test comment says so.
- #830: two inline colon forms that log lines carry and `Block` missed. A
  credential key with no blank after the colon, such as `API_KEY:Zq9xV7mP2wL4`,
  and a credential key after prose on the same line, such as `error: see
  api_key: Zq9xV7mP2wL4 now`, are redacted. The value must be one token of at
  least the minimum secret length, with a letter and a digit, and not a Go
  pointer, which keeps the repository's docs scan clean. The prose guards stay.
  A chain such as `err: api_key: V` is redacted, looking past at most three
  plain keys so the cost stays linear. The stated limit is that an all-letter
  or all-digit value is not caught by this rule.

## Owner steps before the first 3.1 run

Delete nothing this time. Install by temp and rename, from the tag, never from
the working tree (R54):

1. After the two gates are answered and the tag is published, build the tag
   in a scratch worktree (`scripts/build-pi-runtime.sh all` fetches the pi
   runtime, then builds):

   ```sh
   git worktree add ~/scratch-v31rc1 v3.1.0-rc.1 && cd ~/scratch-v31rc1 && scripts/build-pi-runtime.sh all
   ```

   The binary is `build/pi/amq-squad`.
2. From the repository, run `up` from the tag build itself. The `amq-squad`
   on PATH is 3.0.2 and has no `up` verb; the 3.0.2 start command,
   `lead --team --scheduler-seats FILE --trust`, is gone and `up` replaces it.
   `up` installs the source build over the `amq-squad` on PATH by temporary
   name and rename (the running binary is the source, so it is untouched),
   then starts the squad:

   ```sh
   cd ~/code/amq-squad
   ~/scratch-v31rc1/build/pi/amq-squad up --binary ~/scratch-v31rc1/build/pi/amq-squad
   ```

3. If a step refuses, `up` refuses by name and nothing after it runs:
   - `pi_binary_untagged`: the binary does not report a tag. Build it from the
     tag with `scripts/build-pi-runtime.sh`, not from the working tree.
   - `pi_not_embedded`: the binary carries no pi runtime. Build it with
     `scripts/build-pi-runtime.sh` at the tag.
   - `pi_runtime_rejected`: `pi path --json` failed or printed no runtime.
     Rebuild from the tag.
   - `squad_invalid`: squad.yaml does not compile. Fix it. Nothing was
     installed or created.
   - `lead_running`: a live lead holds the root. `up` prints its pid, its pane
     and `tmux attach -t <pane>`. Attach to it. `up` stops nothing.
   - `tmux_unavailable`: tmux could not be asked about the recorded lead's
     pane. Make tmux answer, then run `up` again. Nothing was stopped.
   - `lead_pane_unknown`: tmux lists neither the lead's pane nor its session.
     `up` cannot tell whether the lead is alive, so it stops nothing. Check
     the pane yourself, then run `up` again.
   - `lead_record_unreadable`: `lead.json` cannot be read, so `up` stops
     nothing. Find out why it is unreadable, then run `up` again.
   - `up_running`: another `up` holds `up.lock`. Wait for it.
   - `lock_unsupported`: the filesystem has no advisory locks, naming the lock.
     Run from a filesystem that has them.
   - `amq_root_symlinked`: the AMQ root or the session root is a symlink.
     Replace it with a directory.
   - `doctor_failed`, or the failing row's kind: read the row's name and
     detail, fix the cause and run `up` again. The installed tagged binary, the
     AMQ root and the session stay, and are harmless.
   - `roster_wait_timeout` and `roster_launch_failed`: the lead is running in
     its tmux session. The refusal names the session and the attach command.
4. The day-4 run is the owner-run row of
   [docs/v3-spike/31-evidence/31-1-pr2-up-status-screen.md](v3-spike/31-evidence/31-1-pr2-up-status-screen.md),

## Recorded limits

- The launch budget counts from `up`'s own start, so the 10 second ceiling
  includes the installed binary's doctor and its host probes. If the day-4 run
  shows the doctor eating the budget, the fix is a faster doctor, not a later
  mark.
- A scheduler started by hand has no lower start bound for a relaunch's start.
  A seat with no marks of its current launch, or whose proof predates its
  recorded start, shows null timing and no ceiling check.
- `.amq-squad/team-rules.md` does not list a seat added live until the lead
  proposes the rules again. The add key leaves the rules as the owner approved
  them.
- Between `up`'s identity check and its kill signal, a pid can end and be
  reused. The recorded start stamp bounds the window to the process
  incarnation `up` decided on, and it is inherent to Unix signals.
- No file a seat reads should name the lead handle as a literal. The handle
  comes from squad.yaml through the role text at launch. On day 3,
  `.amq-squad/team-rules.md` said the lead is `cto` while the lead ran as
  `lead`, and a reviewer seat reported the lead inactive. A row that searches
  the compiled seat texts for a literal lead handle is not built yet.
- Until AMQ's ask 20 lands, the add key is a roster relaunch and every live
  seat drains first. On a busy squad the drain counts against the added seat's
  budget and is named in its segments.
- A `lead --team` started outside tmux has no recorded pane. `up` refuses
  `lead_running` for it and never stops it.
