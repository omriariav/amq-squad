# amq-squad v3.2.0-rc.1

These are the notes for the 3.2.0 release candidate 1, built from the tip of
v3 after #903. The candidate is not the release. The notes grow into the
3.2.0 notes. The module path is unchanged:

```sh
go install github.com/omriariav/amq-squad/v3/cmd/amq-squad@v3.2.0-rc.1
```

A `go install` build carries no embedded pi runtime. The binary the squad runs
is built from the tag by `scripts/build-pi-runtime.sh`, as the owner steps
below show. Upgrading from v2: see [MIGRATION.md](../MIGRATION.md). The earlier
notes are [docs/v3.1.2-release-notes.md](v3.1.2-release-notes.md) and the
notes it links.

## What 3.2 is so far

Three fixes to how the squad keeps working on its own. The second and third
come from the squad's own run on this repository on 2026-11-05:

- A Codex seat's lease is now renewed from the seat's own work, as a Claude
  seat's already was, so a working seat no longer loses its task for want of
  a `task renew` call. Every task now has a time budget, and no renewal goes
  past it.
- When the harness refuses a seat's commit ledger as tampered, the refused
  bytes are copied aside before anything else writes. On 2026-11-05 the next
  write overwrote them within seconds.
- The merge train waits for GitHub to finish bringing a PR's branch up to
  date, and proves the new head before it trusts it. Before this, no seat PR
  that was behind its base could land through the train.

## A seat's lease renews from its own work, inside the task's budget (#891)

The execution note is
[docs/v3-spike/320-evidence/activity-renewal.md](v3-spike/320-evidence/activity-renewal.md).

- **Renewal comes from the seat's activity.** Each real work event the seat's
  runtime reports (a tool result in a Claude seat, a `PostToolUse` in a Codex
  seat) renews the lease of the attempt the seat holds. A Codex seat's lease
  is renewed from its own activity, never past the task's budget, with no
  `task renew` call needed, once the owner has trusted its hooks (next
  section). `task renew` still works and does no harm, but it
  is no longer part of a seat's work loop.
- **Only work renews.** A receipt or an evidence post does not renew. An event
  from an earlier attempt does not renew a later attempt of the same task, and
  one seat's events never renew another seat's lease. The scheduler's own
  liveness events no longer renew anything.
- **Every task has a budget.** A task gets the squad's default when it is
  added: the new squad.yaml key `task_budget` (a Go duration such as `90m` or
  `2h`), 90 minutes when the key is absent. `task add --budget DURATION` sets
  one task's budget. The lease of an attempt never runs past the lease's
  grant plus the task's budget, on either renewal path. At the end, renewal is
  refused with `task budget spent` and the lease runs out.
- **The lead extends a budget.** `amq-squad task extend ID --by 30m`, run
  from the lead, with no `--me`: the scheduler proves the lead from the
  process, as for `task widen`. Each extension is recorded on the task and in
  the decision log as `task_budget_extended`.
- **The lead sees the clock.** The scheduler logs one `task_budget_warning`
  when an attempt's budget is one lease (ten minutes) from its end, and
  `task_budget_spent` when it ends. The lead's screen shows the time left on
  a running task's lease and budget once the lease has two minutes left or the
  budget ten.
- **Status carries the budget.** `amq-squad status --json` task rows gain
  `budget` (nanoseconds) and `budget_ends_at`.
- **Tasks from 3.1.2 are stamped once.** A lease written by 3.1.2 has no
  attempt or budget end. The first 3.2 read stamps it with the task's attempt
  and a budget end of the lease's grant plus the default 90 minutes, and logs
  `lease_normalised`. A claimed task with no pending done report whose lease
  was granted more than 90 minutes before the upgrade is over its budget at
  once: it expires on the scheduler's first tick and its seat is closed. A
  later `task extend` raises the allowance for the next attempt and does not
  revive the ended one. Right after the restart the lead extends the tasks
  still inside their 90 minutes that should keep running: step 5 of the owner
  and lead steps below.

----------

**Records.** The contract rows and their revert runs are in the execution
note. A scratch replay of Codex's real `PostToolUse` payload moved a lease's
expiry and wrote its first-renewal decision with no `task renew`. The
model-driven live row runs on the first installed 3.2 build, after the owner's
trust step below.

## The one-time Codex hook trust

A Codex seat reports its work through hooks that amq-squad adds to that seat's
session only (`PostToolUse` and `Stop`, as `-c` session flags). Codex 0.166
runs such a hook only after the owner trusts it, and the trust is tied to the
hook's exact command, which includes the installed `amq-squad` path.

- **After installing, the owner runs Codex's `/hooks` once** to trust the
  amq-squad hook at its real path: launch one Codex seat, run `/hooks` in it,
  and trust the three `/<session-flags>/config.toml` amq-squad activity
  entries. Nothing writes that trust for the owner: amq-squad never writes
  `~/.codex` or the owner's `CODEX_HOME`.
- **Until then, doctor and the seat launch warn**, with the exact commands:

  ```text
  codex seats will not renew on their own until you trust the amq-squad hooks: launch one Codex seat, run /hooks, and trust the three /<session-flags>/config.toml amq-squad activity entries
  ```

  An untrusted Codex seat is told in its task doorbell to run
  `amq-squad task renew --me "$AM_ME"` after every tool batch and at least
  every five minutes, and to stop and block if renewal is refused.
- **A reinstall at another path needs the trust again.** The trust follows the
  real path of the binary, symlinks resolved.
- **The seat's `Stop` hook replaces the owner's.** For a Codex seat's process,
  the session `Stop` hooks replace any `Stop` hooks in the owner's Codex
  config. amq-squad keeps AMQ's own dialog-close command in the replacement,
  byte for byte as AMQ installs it.

Claude seats need no new step: their hooks plugin already reports each tool
result.

## A refused commit ledger keeps its evidence (#887, #893)

The investigation note is
[docs/v3-spike/320-0-ledger/0-ledger-investigation.md](v3-spike/320-0-ledger/0-ledger-investigation.md),
the execution note
[docs/v3-spike/320-0c-quarantine/A-quarantine.md](v3-spike/320-0c-quarantine/A-quarantine.md).

- **What happened.** On 2026-11-05, after a rollback to 3.1.0-rc.1, the
  scheduler refused the reviewer seat's commit ledger as tampered on every
  tick for 65 minutes. The cause was version skew, not tampering: 3.1.1 added
  an `attempt` field to a discarded-commit entry, and rc.1 drops a field it
  does not know, so its seal check fails. 3.1.1 and 3.1.2 accept the same
  ledger (#887). The refused body was lost: the next write re-sealed the
  ledger 2 to 4 seconds later, and the ledger keeps no history.
- **The read that refuses now copies what it refused.** The exact bytes the
  check read (the ledger and its head) go into a new directory under the
  session root, `extensions/amq-squad/quarantine/commits.<seat>.seq<N>/`,
  with a `quarantine.txt` that names the time, the seat, the writer, the
  binary and the refusal (#893). The set appears whole or not at all. The
  same refusal again is one copy; a different body under the same sequence
  gets the next slot (`.2`, `.3`, up to 100).
- **Every writer checks first.** Before any write, the ledger on disk is read
  again under the lock. A refused ledger is not written over, so the next
  writer can no longer destroy the evidence.
- **The refusal says where the copy is.** The error reads `...; the refused
  document is quarantined at <dir>`, or names why the copy failed. It is the
  same `ledger_tampered` refusal as before, so nothing that reacts to it
  changes.
- **A quarantine is evidence only.** Nothing reads it as a ledger.
  `amq-squad uninstall` lists it as session state; `uninstall --write`
  removes it even without `--purge`. Copy any evidence you need before
  uninstalling.

----------

**Limits.** The copy guards against links and against another process's
writes, not against a process running as the owner's own user. Off macOS and
Linux the copy runs by path, without the descriptor checks. Recovering from a
held ledger is not in this candidate (below).

## The merge train waits for GitHub's branch update (#903)

The execution note is
[docs/v3-spike/320-3a-train/async-update.md](v3-spike/320-3a-train/async-update.md).

- **What happened.** On 2026-11-05 the train asked GitHub to bring #894 up to
  date. GitHub's update answers with the old head and moves the branch a few
  seconds later. The train took that answer as the new head, so the task
  stayed bound to the old one, and it refused the moved branch as a force push
  it had not made. Every seat PR is behind at train time, since
  merges are serial, so none could land.
- **The async update.** The train now journals the request before it sends it,
  then reads the PR back until the head moves, waiting 1, 2, 4, 8, then 16
  seconds between reads, up to 120 seconds. It never trusts the update's own
  answer. It then proves the new head: its first parent must be the base tip
  the train asked for, and its patch-id must equal the bound head's. Only then
  is the head bound and merged. A head on any other parent is someone's later
  push and is refused `pr_head_moved`.
- **If GitHub does not move the branch in time**, the PR is refused in words
  under the rule `branch_update_unconfirmed`: nothing is bound and nothing is
  merged. Run the train again; if it repeats, the update may conflict.
- **A run that ends mid-update recovers.** The next run finds the journaled
  request and, when the branch moved by exactly one force push inside the
  request's window and the proof holds, binds the new head. A failed update
  that GitHub refused outright is retired and recovers nothing; one that
  failed without a clear answer stays live and recovers only a proved push
  inside its window. A whole run is bounded, so a stalled call to GitHub ends
  the run with `run_timeout` instead of hanging it.
- **The lead's `merge-train rebind` verb.** When the train refused a head
  that was in fact its own update, the lead re-admits it:

  ```sh
  amq-squad merge-train rebind --pr N --from <bound sha> --to <current sha>
  ```

  Like `task widen`, it takes no `--me`: the scheduler proves the lead from
  the process, and a seat gets `not_lead`. The scheduler checks that one task
  is bound to the PR at `--from` and that the PR's head is `--to`, runs the
  same first-parent and patch-id proof, and writes the binding only while the
  task is still bound at `--from`. A re-bind that finds the binding moved on
  is refused and marks that head superseded; no later run or recovery trusts a
  superseded head until the lead's verb re-admits it. The verb prints the
  proof, or the refusal and its code, and exits 15 on a refusal. The decision
  log gets `merge_train_rebound` or `merge_train_rebind_refused`.
- **The train runs `gh` from the scheduler.** A scheduler started without
  `gh` on its PATH refuses every re-bind with gh's error.

### The interim rule for this candidate

Until a 3.2.x fix, the lead lands a PR through the train only when its task
has no live lease and no queued commit result. The harness's own binding
writes (the commit step's, and the completion of a bound task) do not pass the
train's check of admitted heads, so a commit result cached at the old head
could be applied after the train bound the new one. It is the open item of
round nine in the execution note.

----------

**Limits.** The first-parent proof assumes one commit per task on the seat
branch, which is what the commit step makes; a branch with more commits is
refused after its update and lands only through the owner's gate. The update
classes are read from gh 2.100.0's error text; a gh that words them
differently falls to the safe side, where the request stays live.

## Rolling back to 3.1.2

Do not roll a session back after this build has written a commit or exits
ledger. Those ledgers and their heads now use a raw-bytes seal layout that
v3.1.x and v3.2.0-rc.1 cannot read. `amq-squad up --binary` refuses every
target before v3.2.0-rc.2 with the instruction to roll forward or start a new
session. It also refuses an unparseable or `(devel)` target because its layout
support cannot be established.

This restriction begins only when a session has a raw-layout head. A session
that has not been written by this build retains the earlier behavior.

If an older binary is installed by hand, outside `up --binary`, it interprets
the two-part document as malformed JSON. v3.1.2 reports the commit ledger as
tampered and does not quarantine it. v3.2.0-rc.1 reports it as tampered and
quarantines the commit bytes in a `sequnknown` slot. Both old builds also
refuse the exits ledger. The exact offline tag-build runs are recorded in
[the 0e verifier execution note](v3-spike/320-0e-verifier/execution.md).

What a rollback loses:

- **A 3.1.2 rewrite of a task drops its budget fields**: item 3 of the known
  limits below.
- **3.1.2's train skips the new journal entries.** It reads only its own
  entry kinds, so it does not honour a head this candidate marked superseded,
  and it has the async-update failure of #894 back.
- **A quarantine directory stays.** 3.1.2 neither writes nor reads it.

For a pre-migration session only, roll back to 3.1.2, not to 3.1.0-rc.1 or
earlier: rc.1 refuses a commit ledger whose discarded-commit entries carry
the `attempt` field that 3.1.1 added (#887).

## Known limits in rc.1

1. **Codex lease renewal needs the owner's one-time `/hooks` trust after
   install.** Until the owner trusts the amq-squad entries, a Codex seat must
   still run `amq-squad task renew` itself, as its doorbell tells it.
2. **Install and restart are one step: `up --binary`.** Never install a new
   `amq-squad` onto PATH while an older lead or scheduler runs.
3. **Rolling back to 3.1.2 drops a task's budget fields.** The next time 3.1.2
   rewrites a task, it leaves out the task's `Budget` and `BudgetExtensions`
   and the lease's `Attempt` and `BudgetEndsAt`, which it does not know.
   Nothing is refused. Back on 3.2, such a task reads as the default
   90-minute budget and its lease is stamped again from its grant; a budget
   set with `--budget` or `task extend` is gone.
4. **A seat launch's fetch from origin has no time limit**, as in 3.1.2: the
   `ls-remote` and `fetch` that start a seat's worktree at the base tip run
   with no timeout, so a stalled origin hangs the launch.
5. **The merge train should not land a PR whose seat still holds a live
   attempt on that task.** A finished commit step records its PR binding
   outside the train's check, and the two can race. Until a 3.2.x fix, the
   lead checks this before each land (the interim rule above).
6. **Two pieces wait for rc.2**, after the ledger's "newer writer" check:
   the tamper-alarm recovery verb (#904) and the cancel clean-up (#909).
7. **The lead's screen truncation fix (#908) is not in rc.1**; it does not
   merge before the tag. Without it, an over-wide line on a narrow pane can
   crash the lead (its pi process ends).
8. **`amq-squad uninstall --write` deletes quarantined ledger copies with the
   session**; copy any evidence first.

## Owner and lead steps for 3.2.0-rc.1

Install by temporary name and rename, from the tag, never from the working
tree (R54).

1. After the v3.2.0-rc.1 tag is published, build the tag in a scratch
   worktree:

   ```sh
   git worktree add ~/scratch-v320rc1 v3.2.0-rc.1 && cd ~/scratch-v320rc1 && scripts/build-pi-runtime.sh all
   ```

   The binary is `build/pi/amq-squad`.
2. From the repository, run `up` from the tag build:

   ```sh
   cd ~/code/amq-squad
   ~/scratch-v320rc1/build/pi/amq-squad up --binary ~/scratch-v320rc1/build/pi/amq-squad
   ```

3. Read the lead's first screen and record it in the release evidence
   (RELEASING.md step 6). A dead pane or a `Failed to load extension` line
   means the candidate is not done.
4. Trust the Codex hooks once: in one Codex seat's pane, run `/hooks` and
   trust the three `/<session-flags>/config.toml` amq-squad activity entries.
   `amq-squad doctor` stops warning when they are trusted.
5. **The lead, right after the restart.** Every task in progress when 3.2
   first reads it is stamped with a budget end of its lease's grant plus 90
   minutes. Right after the restart, the lead extends every in-progress task
   that should keep running (`amq-squad task extend ID --by DURATION`),
   before its lease runs out. Extending a budget is the lead's decision. A
   claimed task with no pending done report whose lease was granted more than
   90 minutes before the restart is already past its budget end: the
   scheduler's first tick expires it (`task_budget_spent`), closes its seat
   and puts the task back to pending. A later `task extend` raises the
   allowance for the task's next attempt; it does not revive the ended one.

The live rows that wait for this install are the model-driven renewal row, in
the #891 note (the lead records `hooks/list`, the ingest line, the lease
expiry before and after and the first-renewal decision, with no `task
renew`), and the re-bind of #894 through `merge-train rebind`, in the #903
note.
