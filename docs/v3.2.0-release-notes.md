# amq-squad v3.2.0-rc.2

These are the notes for the 3.2.0 release candidate 2, built from the tip of
v3 after #962 (`e27dca44f638d47fd4df2c9cbe35a9b029a30ea5`). The candidate is
not the release. The notes grow into the 3.2.0 notes. The module path is
unchanged:

```sh
go install github.com/omriariav/amq-squad/v3/cmd/amq-squad@v3.2.0-rc.2
```

A `go install` build carries no embedded pi runtime. The binary the squad runs
is built from the tag by `scripts/build-pi-runtime.sh`, as the owner steps
below show. Upgrading from v2: see [MIGRATION.md](../MIGRATION.md). The earlier
notes are [docs/v3.1.2-release-notes.md](v3.1.2-release-notes.md) and the
notes it links. The rc.1 form of these notes is this file at the
`v3.2.0-rc.1` tag.

## What 3.2 is so far

Fixes to how the squad keeps working on its own. The second through fourth
come from the squad's own run on this repository on 2026-11-05:

- A Codex seat's lease is now renewed from the seat's own work, as a Claude
  seat's already was, so a working seat no longer loses its task for want of
  a `task renew` call. Every task now has a time budget, and no renewal goes
  past it.
- When the harness refuses a seat's commit ledger as tampered, the refused
  bytes are copied aside before anything else writes. On 2026-11-05 the next
  write overwrote them within seconds.
- A tamper alarm now holds that seat once per alarm, and the lead can recover the exact
  quarantined slot through `amq-squad scheduler recover`. Recovery continues
  the authenticated chain on the raw layout, records the decision and any
  checked carried commits, and leaves the quarantine intact as evidence.
- The merge train waits for GitHub to finish bringing a PR's branch up to
  date, and proves the new head before it trusts it. Before this, no seat PR
  that was behind its base could land through the train.
- The merge train no longer asks the owner to approve a result that GitHub's
  own rules or an already-finished merge make impossible to act on.
- Commit and exits ledgers seal their exact bytes and their heads. A newer
  authenticated schema is now an install or writer decision, not a false
  tamper alarm, and an incompatible seat no longer blocks healthy peers.
- A cancelled seat is now closed, its work archived and its worktree cleaned
  before the slot is released.
- Recovery now permanently retires its quarantine slot, so replaying identical
  refused bytes creates a new slot and cannot reuse an earlier recovery to
  release a later hold.
- With a live scheduler, `task claim` acknowledges only the scheduler's offer
  to the same holder, and a claim checks the seat's serving pool.
- The lead's screen passes every line it returns through a width cut before
  it counts it.
- `SeatHandle` now refuses controls and invalid UTF-8, and the status
  contract replaces every C0 and C1 control at its single exit. Plain task
  list and show output use the same replacement.
- The merge train now reads a PR's diff that holds terminal escape bytes, and
  skips a gate record of a kind this build no longer carries.
- `amq-squad up --binary` checks the session's sealed ledger layout in its
  install step, before it installs a build.

## A seat's lease renews from its own work, inside the task's budget (#891, #932, #952, #954)

The execution note is
[docs/v3-spike/320-evidence/activity-renewal.md](v3-spike/320-evidence/activity-renewal.md).
The renewal labels and the Codex admission (#952, #954) are in
[docs/v3-spike/320-renewal-ab/execution.md](v3-spike/320-renewal-ab/execution.md),
the upgrade stamp (#932) in
[docs/v3-spike/320-normalise/execution.md](v3-spike/320-normalise/execution.md).

- **Renewal comes from the seat's activity.** Each real work event the seat's
  runtime reports (a tool result in a Claude seat, a `PostToolUse` in a Codex
  seat) renews the lease of the attempt the seat holds. A Codex seat's lease
  is renewed from its own activity, never past the task's budget, with no
  `task renew` call needed, once the owner has trusted its hooks (next
  section). `task renew` still works and does no harm, but it
  is no longer part of a seat's work loop.
- **Renewal provenance is visible.** A live lease records its total renewals,
  how many came from runtime activity and how many were manual, plus the most
  recent source. `task show` prints all three counts. A lease written by an
  earlier candidate keeps its unlabelled total, and its first labelled
  activity still records the attempt's one first-activity decision.
- **Only work renews.** A receipt or an evidence post does not renew. An event
  from an earlier attempt does not renew a later attempt of the same task, and
  one seat's events never renew another seat's lease. The scheduler's own
  liveness events no longer renew anything.
- **Every task has a budget.** A task gets the squad's default when it is
  added: the new squad.yaml key `task_budget` (a Go duration such as `90m` or
  `2h`), 90 minutes when the key is absent. `task add --budget DURATION` sets
  one task's budget. The lease of an attempt never runs past the lease's
  grant plus the task's budget, on either renewal path. At the end, renewal is
  refused with `task budget spent` and the lease runs out.
- **The lead extends a budget.** `amq-squad task extend ID --by 30m`, run
  from the lead, with no `--me`: the scheduler proves the lead from the
  process, as for `task widen`. Each extension is recorded on the task and in
  the decision log as `task_budget_extended`.
- **The lead sees the clock.** The scheduler logs one `task_budget_warning`
  when an attempt's budget is one lease (ten minutes) from its end, and
  `task_budget_spent` when it ends. The lead's screen shows the time left on
  a running task's lease and budget once the lease has two minutes left or the
  budget ten.
- **Status carries the budget.** `amq-squad status --json` task rows gain
  `budget` (nanoseconds) and `budget_ends_at`.
- **Tasks from 3.1.2 are stamped once (#932).** A lease written by 3.1.2 has
  no attempt or budget end. The first 3.2 read stamps it with the task's
  attempt and a budget end, and logs `lease_normalised`. On the upgrade
  the budget end is the later of the grant plus the task's budget (90 minutes for a 3.1.2 row) and the restart plus one lease (ten minutes):
  the budget end is at least one lease after the restart; the lease's own expiry is unchanged, so a seat that is not renewing still ends as lease_expired,
  and the scheduler's tick logs task_budget_warning. A later `task extend`
  raises the allowance for the next attempt and does not revive an ended
  attempt. Right after the restart the lead extends the tasks that should keep
  running: step 5 of the owner and lead steps below.

----------

**Records.** The contract rows and their revert runs are in the execution
note. A scratch replay of Codex's real `PostToolUse` payload moved a lease's
expiry and wrote its first-renewal decision with no `task renew`. The
model-driven live row ran on the installed rc.1 build, on task t109: its row
and decision logs are in the rc.1 release evidence
([docs/v3-spike/5-release-evidence/release-v3.2.0-rc.1/](v3-spike/5-release-evidence/release-v3.2.0-rc.1/README.md),
"t109 is the proof").

## The one-time Codex hook trust

A Codex seat reports its work through hooks that amq-squad adds to that seat's
session only (`PostToolUse` and `Stop`, as `-c` session flags). Codex 0.166
runs such a hook only after the owner trusts it, and the trust is tied to the
hook's exact command, which includes the installed `amq-squad` path.

- **After installing, the owner runs Codex's `/hooks` once** to trust the
  amq-squad hook at its real path: launch one Codex seat, run `/hooks` in it,
  and trust the three `/<session-flags>/config.toml` amq-squad activity
  entries. Nothing writes that trust for the owner: amq-squad never writes
  `~/.codex` or the owner's `CODEX_HOME`.
- **Until then, doctor and the seat launch warn**, with the exact commands:

  ```text
  codex seats will not renew on their own until you trust the amq-squad hooks: launch one Codex seat, run /hooks, and trust the three /<session-flags>/config.toml amq-squad activity entries
  ```

  An untrusted Codex seat is told in its task doorbell to run
  `amq-squad task renew --me "$AM_ME"` after every tool batch and at least
  every five minutes, and to stop and block if renewal is refused. That
  fallback is removed as soon as the seat's own hook ledger shows one tool
  result since its launch; a doorbell at which that ledger cannot be read
  carries it again; another seat's activity never removes it, and a relaunch
  starts a new proof window.
  Every seat's doorbell also says that a command longer than the ten-minute
  lease must run in the background and be polled.
- **A reinstall at another path needs the trust again.** The trust follows the
  real path of the binary, symlinks resolved.
- **The seat's `Stop` hook replaces the owner's.** For a Codex seat's process,
  the session `Stop` hooks replace any `Stop` hooks in the owner's Codex
  config. amq-squad keeps AMQ's own dialog-close command in the replacement,
  byte for byte as AMQ installs it.

Claude seats need no new step: their hooks plugin already reports each tool
result.

## A refused commit ledger keeps its evidence (#887, #893)

The investigation note is
[docs/v3-spike/320-0-ledger/0-ledger-investigation.md](v3-spike/320-0-ledger/0-ledger-investigation.md),
the execution note
[docs/v3-spike/320-0c-quarantine/A-quarantine.md](v3-spike/320-0c-quarantine/A-quarantine.md).

- **What happened.** On 2026-11-05, after a rollback to 3.1.0-rc.1, the
  scheduler refused the reviewer seat's commit ledger as tampered on every
  tick for 65 minutes. The cause was version skew, not tampering: 3.1.1 added
  an `attempt` field to a discarded-commit entry, and rc.1 drops a field it
  does not know, so its seal check fails. 3.1.1 and 3.1.2 accept the same
  ledger (#887). The refused body was lost: the next write re-sealed the
  ledger 2 to 4 seconds later, and the ledger keeps no history.
- **The read that refuses now copies what it refused.** The exact bytes the
  check read (the ledger and its head) go into a new directory under the
  session root, `extensions/amq-squad/quarantine/commits.<seat>.seq<N>/`,
  with a `quarantine.txt` that names the time, the seat, the writer, the
  binary and the refusal (#893). The set appears whole or not at all. The
  same refusal again is one copy; a different body under the same sequence
  gets the next slot (`.2`, `.3`, up to 100).
- **Every writer checks first.** Before any write, the ledger on disk is read
  again under the lock. A refused ledger is not written over, so the next
  writer can no longer destroy the evidence.
- **The refusal says where the copy is.** The error reads `...; the refused
  document is quarantined at <dir>`, or names why the copy failed. It is the
  same `ledger_tampered` refusal as before, so nothing that reacts to it
  changes.
- **A quarantine is evidence only.** Nothing reads it as a ledger. Since
  #934, `amq-squad uninstall` lists it in the sealed ledgers group beside the
  commits ledger: `uninstall --write` alone keeps it, and `--purge` removes
  it with the ledger.

----------

**Limits.** The copy guards against links and against another process's
writes, not against a process running as the owner's own user. Off macOS and
Linux the copy runs by path, without the descriptor checks. Recovering from a
held ledger is the next section.

## A tamper alarm holds the seat once, and the lead recovers it (#934, #936, #938, #939, #940, #941)

The execution note is
[docs/v3-spike/320-0c-quarantine/B-recovery.md](v3-spike/320-0c-quarantine/B-recovery.md).
It replaces #904, which did not merge.

- **The hold and the recovery.** A tamper alarm holds the seat once per
  alarm, and the lead recovers the exact quarantined slot through
  `scheduler recover`. The decision is recorded, recovery writes the raw
  sealed layout, checked commits may be carried, and the quarantine remains
  evidence.
- **The verb.** Like `task widen`, it takes no `--me`: the scheduler proves
  the lead from the process.

  ```sh
  amq-squad scheduler recover --seat H --seq N [--slot K] [--carry TASK:COMMIT] --reason R
  amq-squad scheduler recover --seat H --alarm ID --reason R
  ```

  The first form recovers the slot `commits.H.seqN.K` (`--slot` is 1 for the
  first slot); the second is a decision by alarm, on a ledger that verifies
  now, with the alarm id from the seat's stop line.
- **A slot is never reused.** Recovery now permanently retires its quarantine
  slot, so replaying identical refused bytes creates a new slot and cannot
  reuse an earlier recovery to release a later hold.
- **The reply says what answers a hold.** When a successful slot recovery
  does not answer the current hold, the reply says which action does: `the
  hold on seat <h> names slot <X>; recover <X>, or send the alarm decision
  (alarm <id>)`, or, for a hold with no slot, `the hold on seat <h> has no
  slot; send the alarm decision (alarm <id>)`.
- **Refusals.** A failed read of the evidence refs refuses
  `recover_base_unobserved`. A `newer_writer` or `schema_mismatch` ledger
  refuses `recover_incompatible`.

## The merge train waits for GitHub's branch update (#903)

The execution note is
[docs/v3-spike/320-3a-train/async-update.md](v3-spike/320-3a-train/async-update.md).

- **What happened.** On 2026-11-05 the train asked GitHub to bring #894 up to
  date. GitHub's update answers with the old head and moves the branch a few
  seconds later. The train took that answer as the new head, so the task
  stayed bound to the old one, and it refused the moved branch as a force push
  it had not made. Every seat PR is behind at train time, since
  merges are serial, so none could land.
- **The async update.** The train now journals the request before it sends it,
  then reads the PR back until the head moves, waiting 1, 2, 4, 8, then 16
  seconds between reads, up to 120 seconds. It never trusts the update's own
  answer. It then proves the new head: its first parent must be the base tip
  the train asked for, and its patch-id must equal the bound head's. Only then
  is the head bound and merged. A head on any other parent is someone's later
  push and is refused `pr_head_moved`.
- **If GitHub does not move the branch in time**, the PR is refused in words
  under the rule `branch_update_unconfirmed`: nothing is bound and nothing is
  merged. Run the train again; if it repeats, the update may conflict.
- **A run that ends mid-update recovers.** The next run finds the journaled
  request and, when the branch moved by exactly one force push inside the
  request's window and the proof holds, binds the new head. A failed update
  that GitHub refused outright is retired and recovers nothing; one that
  failed without a clear answer stays live and recovers only a proved push
  inside its window. A whole run is bounded, so a stalled call to GitHub ends
  the run with `run_timeout` instead of hanging it.
- **The lead's `merge-train rebind` verb.** When the train refused a head
  that was in fact its own update, the lead re-admits it:

  ```sh
  amq-squad merge-train rebind --pr N --from <bound sha> --to <current sha>
  ```

  Like `task widen`, it takes no `--me`: the scheduler proves the lead from
  the process, and a seat gets `not_lead`. The scheduler checks that one task
  is bound to the PR at `--from` and that the PR's head is `--to`, runs the
  same first-parent and patch-id proof, and writes the binding only while the
  task is still bound at `--from`. A re-bind that finds the binding moved on
  is refused and marks that head superseded; no later run or recovery trusts a
  superseded head until the lead's verb re-admits it. The verb prints the
  proof, or the refusal and its code, and exits 15 on a refusal. The decision
  log gets `merge_train_rebound` or `merge_train_rebind_refused`.
- **The train runs `gh` from the scheduler.** A scheduler started without
  `gh` on its PATH refuses every re-bind with gh's error.

### The interim rule for this candidate

Until a 3.2.x fix, the lead lands a PR through the train only when its task
has no live lease and no queued commit result. The harness's own binding
writes (the commit step's, and the completion of a bound task) do not pass the
train's check of admitted heads, so a commit result cached at the old head
could be applied after the train bound the new one. It is the open item of
round nine in the execution note.

----------

**Limits.** The first-parent proof assumes one commit per task on the seat
branch, which is what the commit step makes; a branch with more commits is
refused after its update and lands only through the owner's gate. The update
classes are read from gh 2.100.0's error text; a gh that words them
differently falls to the safe side, where the request stays live.

## The merge train asks only actionable owner questions (#927, #929)

The execution note is
[docs/v3-spike/320-train-gates/train-gates.md](v3-spike/320-train-gates/train-gates.md).

- **GitHub's strict rule has no owner override.** If required status checks
  demand an up-to-date branch and the train cannot update it, the train
  refuses the PR in words and raises no gate. An accepted grow-merge gate
  left by an earlier run is ignored for this rule.
- **A branch conflict is its own refusal.** An update GitHub rejects because
  the branch conflicts with the base is `update_conflict`, not the strict
  policy rule. It raises no gate. The lead closes the PR and has the task
  redone on the current base; a seat never merges the base by hand.
- **A PR merged at another head is terminal for that binding.** The first run
  records the reconcile mismatch and one `pr_state` refusal with the server
  head, the distinct merge commit, the bound head and the task. Later runs
  skip that same task binding without reading or auditing the PR again. A
  changed binding is checked afresh.
- **One unreadable PR does not stop the batch before mutation.** Planning
  reads of the PR, its diff, checks, stable-head re-read and base comparison,
  plus rebind, update and merge recovery proof reads, use the same read
  policy. Bare EOF, 5xx, transport, deadline, killed `gh`, unknown wording
  and exact HTTP 4xx other than 401, 403 or 404 write
  `reconcile_read_failed`, skip that PR and continue. Exact-wrapper 401 and
  403 end the run with authentication and access guidance; 404 keeps its
  prior fatal behavior. An unfamiliar wrapper stays on the safe skip side.
  One recovery path is deliberately stricter: a non-definite Checks error in
  `waitCI` inside `reconcileUpdates` ends the run in the recovery words instead
  of skipping the PR. This is safe-direction behavior and nothing merges.
- **An unreadable state after mutation stops the batch.** Once an update is
  requested or a merge is sent by this run, a non-definite head, proof or CI
  read failure ends the run in words instead of planning the next PR against
  an uncertain base. A transient branch-update read failure does not override
  a later read that sees the head moved; if no read sees a move before the
  deadline, the failure stops the run. The next run recovers the PR from the
  journal before continuing.
- **A pending merge intent recognizes a merge at another head immediately.**
  It records the reconcile mismatch and terminal `pr_state` refusal without
  reading that merged PR's diff or checks.
- **The lead's train stop fits the screen.** Strict, conflict and
  merged-elsewhere instructions are each under the screen's 200-character
  limit. Full refusal details remain in the plan and decision record, and a
  merged-elsewhere stop names the task from that record instead of saying
  only to check the PR. When several rules are present, the screen selects
  the most important instruction in fixed order: update conflict, strict
  policy, and then merged elsewhere only when the detail says the PR already
  merged at another head. A plain `pr_state` keeps the existing first-rule
  order. The detail still carries every rule.
- **Actionable growth refusals are unchanged.** Size caps and the other rules
  that an owner can safely widen still raise their existing grow-merge gate.

## Raw-byte ledger seals and compatible seat exclusion

The commit and exits ledgers now store a JSON body followed by a separately
authenticated seal line. The seal covers the exact body bytes, sequence,
previous tag, writer version and schema. Their heads use the same raw layout,
and a head tag is verified before strict decoding. A verified unknown field is
classified by schema as `newer_writer` or `schema_mismatch`; edited bytes,
skipped links and mismatched previous tags remain tampering.

Legacy ledgers migrate on their next write. If that write is interrupted
after the raw document lands but before its head, readers accept only the
authenticated immediate successor of the legacy head and do not write. The
next locked writer reads and verifies again, records the migration durably,
then completes the head. A crash between the record and head write is retried
without a duplicate record. Both commit quarantine and exits reconciliation
use the exact head bytes they read, even if the live head changes before the
check.

Uninstall and status also read both layouts. Uninstall recognizes idle and
active commit queues from the raw-layout exits ledger, retaining the busy
check's malformed-file refusal, and lists worktree candidates from raw-layout
commit ledgers while skipping malformed commit ledgers.
Status preserves the missing-push-URL warning from a raw-layout commit ledger
instead of silently skipping the seat.

A seat whose commit ledger needs a newer reader or has a verified schema
mismatch is excluded from dispatch rather than blocking a task. Healthy seats
of the pool continue taking work. The exclusion is logged once and clears when
the installed reader verifies the ledger, or when the lead recovers the seat.
The refusal is not a failed attempt and never escalates its routing pool.

The screen names the writer version from the authenticated record and tells
the owner to run `amq-squad up --binary <that build>`. Version comparison
rejects leading-zero core versions and accepts build metadata without giving
it precedence.

The contract, compatibility probes and revert evidence are in
[the 0e verifier execution note](v3-spike/320-0e-verifier/execution.md).

## A claim takes the scheduler's offer, inside the seat's pool (#901, #912)

The note is [docs/v3-spike/320-2a-claim/2a.md](v3-spike/320-2a-claim/2a.md).
It has no "Release note" heading; this section is written from its "Result"
section. #901 carries #899, which did not merge; #912 adds a row and changes
no product code.

- **With a live scheduler, a claim takes its offer.** A live scheduler is
  proved only by its launch record's PID still being alive with the same raw
  process-start stamp. On that path an ID claim acknowledges only the live,
  unclaimed offer for the same holder, while a claim without an ID is refused
  in words: "the scheduler hands out work; wait for its offer". A missing
  record, a gone PID, or a mismatched start stamp takes the compatibility
  path.
- **A seat claims only work its pool serves.** On the compatibility path a
  known seat pool can claim only work it serves. An unknown seat pool fails
  closed on pinned work with `claim_pool_unknown` and the words "ID is pinned
  to POOL; claim it with --pool, or let the scheduler hand it out"; an
  unpinned task remains claimable. Pull-next uses the same filter and never
  selects a task pinned to another pool.
- **A claim never moves a routing decision.** A claim checks the seat's
  serving pool and never moves an existing routing decision. After a failed
  attempt escalates, the next grant records the new tier's pool.
- **`--pool` and the launch record.** When a live launch record and `--pool`
  disagree, the CLI refuses the mismatch in words.
- **A lapsed holder.** A lapsed holder is excluded for the current seat
  launch only. A real seat relaunch clears the old exclusion.
- **The refusal names** are `claim_offer_required`, `claim_offer_expired`,
  `claim_pool_mismatch` and `claim_pool_unknown`. The CLI prints their plain
  words above the refusal rule.

## The lead's screen fits the pane (#955, #957)

The note is
[docs/v3-spike/320-0d-screen/README.md](v3-spike/320-0d-screen/README.md).
It has no "Release note" heading; this section is written from its sections.
PR #955 replaces #950, which replaced #908; neither of those merged.

- **Every line fits the pane's width.** An over-wide line either crashed the
  lead's regular-mode screen or broke the measured fit, depending on the
  redraw path. The screen now passes every returned line through the local
  `truncateToWidth` before counting it: fixed lines, task lines, record
  lines, closed and overflow tails, the stale-error line, and the
  fixed-overflow message. A cut task or record keeps its id and plain words.
- **The screen measures rather than predicts.** It renders task caps from
  largest to smallest and keeps the largest rendered screen that fits. When
  fixed content alone exceeds the pane, it draws the first `rows - 1` lines
  and ends with `… N more lines; enlarge the pane`.
- **Live work first.** The task window puts blocked, then in-progress, then
  pending work first. An open overflow ends with `+N more (/team for all)`,
  and when open tasks fill the window exactly, closed tasks fold into
  `N closed`.
- **A file-lock wait names its holder.** A pending task waiting on a file
  lock reads `t26 waits for t71: both declare docs/v3-spike/320-evidence/`,
  and `task add` reports the same wait in text and JSON (`t2 will wait for
  t1: both declare docs/x.md`). In `status --json`, `waits_for` holds one
  `{task_id, path}` per holder for a pending `file_lock` wait.
- **`pin_unresolved` names the class chain.** The block carries the pinned
  class chain, and the screen keeps the pin whole and ends a shortened chain
  with `, +N more`.
- **One decision per wait change.** A wait change writes one `wait_changed`
  decision, not one per tick.
- **Control characters (#957).** Task and block text reaches the screen
  through `clean()`, which replaces U+0000 through U+001F and U+007F through
  U+009F with a space. Since #957 the line shown before any status is read
  and every line of the expanded screen replace the same characters.

## Control characters a seat writes stay off the terminal (#959, #960)

The note is
[docs/v3-spike/320-control-bytes/README.md](v3-spike/320-control-bytes/README.md),
as #960 corrected it. It has no "Release note" heading; this section is
written from its sections. #959 replaces #958, which did not merge.

- **Seat handles.** A seat handle is trimmed first, then refused when it is
  empty or path-like, is not valid UTF-8, or holds any rune below U+0020 or
  from U+007F through U+009F. A grant to such a handle is refused, and the
  task stays pending without a lease.
- **The status document.** `amq-squad status`, plain and `--json`, replaces
  each C0 or C1 control with one space at its single exit, after credential
  redaction; invalid UTF-8 becomes U+FFFD. Gate questions alone keep their
  line breaks.
- **`task list` and `task show`.** The plain output passes every stored
  string through the same replacement; a description alone keeps its line
  breaks. JSON remains the stored contract and relies on JSON escaping.
- **The fleet warning.** The warning for a squad whose root is unavailable is
  replaced the same way.
- **`task block` refuses the scheduler's reason.** `task block --reason
  ledger_tampered` is refused before the store is called: `ledger_tampered is
  the scheduler's; a seat blocks with its own reason`.

What still prints a seat's text unchanged is under the known limits below.

## Upgrading from rc.1 or 3.1.2

Install rc.2 with `up --binary`, as the owner and lead steps below show.

- **The sealed ledgers migrate on their next write, once.** A read does not
  migrate a ledger. The next ordinary current write completes each legacy or
  interrupted ledger migration with exactly one migration record; both commit
  heads and the exits head become raw with a larger sequence, and existing
  rc.1 quarantine files stay byte-equal. Frozen rc.1 commit and exits bytes
  remain readable and migrate once. The raw layout is described under
  "Raw-byte ledger seals" above.
- **What an older binary answers after that.** Installing either older
  version over a completed raw-layout migration makes its commit and exits
  readers report `ledger_tampered`. If an older binary is installed by hand,
  outside `up --binary`, it interprets the two-part document as malformed
  JSON. v3.1.2 reports the commit ledger as tampered and does not quarantine
  it. v3.2.0-rc.1 reports it as tampered and quarantines the commit bytes in
  a `sequnknown` slot. Both old builds also refuse the exits ledger. The
  exact offline tag-build runs are recorded in
  [the 0e verifier execution note](v3-spike/320-0e-verifier/execution.md).
- **So do not roll a session back after this build has written a commit or
  exits ledger.** `amq-squad up --binary` refuses every target before
  v3.2.0-rc.2 with `ledger_layout_downgrade` and the instruction to roll
  forward or start a new session. It also refuses an unparseable or
  `(devel)` target because its layout support cannot be established. This
  restriction begins only when a session has a raw-layout head or an
  authenticated interrupted migration. A session that has not been written
  by this build retains the earlier behavior.
- **Tasks.** A lease from 3.1.2 is stamped once, as the first section says;
  right after the restart the lead extends the tasks that should keep
  running (step 5 below). A lease written by rc.1 keeps its renewal total as
  unlabelled renewals.

## Known limits in rc.2

### Kept from rc.1

1. **Codex lease renewal needs the owner's one-time `/hooks` trust after
   install.** Until the owner trusts the amq-squad entries, a Codex seat must
   still run `amq-squad task renew` itself, as its doorbell tells it.
2. **Install and restart are one step: `up --binary`.** Never install a new
   `amq-squad` onto PATH while an older lead or scheduler runs.
3. **Rolling back to 3.1.2 drops a task's budget fields.** The next time 3.1.2
   rewrites a task, it leaves out the task's `Budget` and `BudgetExtensions`
   and the lease's `Attempt` and `BudgetEndsAt`, which it does not know.
   Nothing is refused where `up --binary` still allows the downgrade (see
   Rolling back). Back on 3.2, such a task reads as the default 90-minute
   budget and its lease is stamped again from its grant; a budget set with
   `--budget` or `task extend` is gone.
4. **A seat launch's fetch from origin has no time limit**, as in 3.1.2: the
   `ls-remote` and `fetch` that start a seat's worktree at the base tip run
   with no timeout, so a stalled origin hangs the launch.
5. **The merge train should not land a PR whose seat still holds a live
   attempt on that task.** A finished commit step records its PR binding
   outside the train's check, and the two can race. Until a 3.2.x fix, the
   lead checks this before each land (the interim rule above).

Removed from rc.1's list: its 6, the two pieces that waited for rc.2 (the
tamper-alarm recovery, #934, which replaces #904; the cancel clean-up, #943,
which replaces #909); its 7, the screen truncation (#955 and #957); its 8,
`uninstall --write` deleting quarantined ledger copies (#934).

### Named for rc.2

6. **Buzz.** On a busy host an answer or a routed message sent through Buzz can come back `rejected (native_error)`. Nothing was delivered; send it again. In the eight measured runs that could send again (four on each version, at a 5 ms poll), one message needed a third send. Cause: a race in amq-remote, measured on 0.116.2 and on v0.138.0, so upgrading amq-remote does not close it; the report is drafted for upstream.
7. **The Codex drain approval.** A Codex seat cannot drain its mailbox or claim a task without an approval prompt, because a Codex seat is launched with `writable_roots=[]` (set at `internal/seatexec/codex.go:29`, required at `internal/seatexec/seatexec_unix.go:575-597`). On rc.1 the dev seat (codex, gpt-5.6-terra) could not drain its mailbox or claim. Making the seat's own mailbox directory and the lock paths writable waits for 3.2.x.
8. **The AMQ pin.** amq-squad 3.2.0 links the AMQ module at v0.116.2 (`go.mod:7`, `internal/adoptionseam/floor.go:21`), and that is the supported pin. It cannot move past v0.138.0 yet: AMQ v0.139.0 removed `launchapi.Inspect`, which the seat liveness check calls (`internal/cli/liveness.go:209`, `:247`). Replacing that call is a 3.3.0 item.
9. **A command longer than the lease loses it.** A seat's lease is ten
   minutes, and a command that runs longer than the lease loses it. From rc.2
   every seat's doorbell says so, once: "A command that runs longer than the
   lease (10m0s) loses it: run long work in the background and poll it."
   On 2026-11-10 a seat's single 22-minute command cost the seat, a roster
   relaunch and the attempt's work. The fix is planned for 3.3.0; until then
   a brief tells a seat that no single command runs longer than 8 minutes.
10. **Control bytes.** rc.2 refuses a seat handle with a control character,
    replaces control characters at the status document's one exit, in plain
    `task list` and `task show`, and in the fleet warning, and `task block`
    refuses the reason `ledger_tampered`. These wait for 3.2.x, by name: the
    entry checks where a pool, a declared file or a root enters; `actor()`;
    holders already on disk; and the exits the control-bytes note's table
    marks "3.2.x item" (Buzz phone replies, gate questions and alerts; the
    seat doorbell and lead notice; the other task verbs' results and
    refusals; `up`'s decision outcome and refusal; the scheduler's stdout
    lines; the merge train's plan and refusals; the fleet document's own
    fields; the decisions log's human readers). The block-code map at
    `internal/routing/refusal.go:18-71` holds 37 names, eleven of them with
    no product writer that writes them to the store as a block code, and
    `task block` reserves only `ledger_tampered`, so a caller who meets the
    store's tests can still type any of the eleven as `task block --reason`.
11. **The merge train's dry run writes.** A dry run still writes its
    protection, batch and plan entries to the audit log, marked as a dry run.
    A dry run also removes a store alert: the drift pass runs before any
    dry-run check and writes and removes alert files on a dry run, and #953
    adds a reason to remove. Making the dry run write nothing under `alerts/`
    waits for 3.2.x.
12. **Stop the team before a downgrade.** Stop the team (the lead and its scheduler) before `amq-squad up --binary` to an older build: `up` reads the ledgers once at its install step, before it stops anything, so a legacy-only session can be migrated by the still-running scheduler after the check passes.
    No row covers this. The 3.2.x items for it are in the rollback note's
    [Limits (round 2)](v3-spike/320-rc2-rollback/execution.md#limits-round-2)
    and in [the 3.2.x list](v3-followups.md#32x).
13. **Two skew rows do not exist.** The per-seat alarms file
    (`commits/<handle>.alarms.jsonl`, new in rc.2) has no row for an older
    reader. By the lead's reading of v3.2.0-rc.1 and v3.1.2, checked by

### From the Limits sections of the rc.2 notes

The tamper-alarm recovery
([B-recovery.md](v3-spike/320-0c-quarantine/B-recovery.md)):

14. **An orphaned tamper block.** A crash between `blockOnTamper`'s
    task-store write and the tick's state write can leave a task blocked for
    an alarm no restored hold carries. The lead uses `amq-squad task reset ID`
    for that task; durable repair is a 3.2.x item.
15. **A crash between the recovery's two writes.** It costs a second decision
    only where the reader refuses the new body under the old head; where the
    old head is intact and the body is its immediate successor, the recovery
    is already committed and the retry or the next write finishes it. Under a
    raw head, the retry deliberately leaves that head behind. The next
    ordinary writer derives its predecessor from the head and writes a
    replacement N+1: the chain stays consistent and carries the recovery, but
    the crashed successor's own sealed link is never completed.
16. **The evidence anchor.** Its `update-ref` passes no expected-old value.
17. **Duplicate migration lines.** After a second decision on a refused
    legacy form, the decisions log can hold more than one migration line.
    They are informational, each is deduped at its own sequence, and nothing
    is granted or lost.
18. **An untagged legacy body carries nothing.** Carry refuses
    `recover_entry_unknown`; recovery with no carry succeeds at N+1 and the
    new ledger holds zero commits.
19. **A stray copy after a crash.** A crash after the mark can leave the
    stray identical copy X.2, while the hold still names X. If a recovery
    records X.2, the decision is recorded and the hold stays, and the reply
    names the way out. One refusing reader can list a slot just before its
    mark is created and still return that slot; the recovery record covers
    its hold.
20. **The mark.** Marked slots count toward the existing limit of 100. A
    process running as the same user can remove the mark, as it can replace
    the whole ledger and head.

The cancel and the clean
([2b-1.md](v3-spike/320-2b-cancel-clean/2b-1.md)):

21. **A superseded cancellation is recorded as cleaned.** When a grant with
    no live scheduler lands after an old cancellation, the later lease makes
    that cancellation superseded and the scheduler records `cleaned_at` even
    though no clean ran. The next preparation remains responsible for archive
    and worktree safety.
22. **A reserved seat still pays its prepare** before the locked grant
    refuses it, and one task can cost one prepare per failing seat in its
    pool per tick as the scheduler skips through the pool, with each distinct
    failure logged once.

The renewal labels and the Codex admission
([execution.md](v3-spike/320-renewal-ab/execution.md)):

23. **An untrusted seat that never calls a tool** keeps the manual-renew
    sentence. This is the safe side.
24. **"Once per attempt" does not survive an rc.1 rewrite of the task**
    because the labels are dropped; the next activity renewal logs once more
    with the unlabelled suffix.
25. **A decision append error is ignored** by the hook ingest
    (`internal/cli/hook_ingest.go`).
26. **An adopted seat.** A seat adopted by the scheduler instead of launched
    gains no admission and keeps the sentence until a launch.
27. **A failed launch.** Admission is recorded before the launch is
    compiled, and the launch time is taken before the seat process starts. A
    failed launch leaves an admission for a seat that is not running, and its
    proof window opens early.
28. **Every ring of an unproven Codex seat scans its whole hook ledger.**

The merge train's escape bytes and legacy records
([note.md](v3-spike/320-train-escape-legacy/note.md)):

29. **A failed proof before the update does not end the run:** the train
    journals `reconcile_read_failed`, skips the PR and goes on.
30. **`doctor` clears the alert too.** The removal is in the drift reader,
    so a `doctor` run that reads the record also removes the alert, and
    writes no `alert_cleared` entry.
31. **What clears nothing.** The first run for a repository writes the
    baseline and returns before any store is read, so it notes nothing and
    clears nothing. An alert that names a session root or the parent of the
    sessions is never removed. A gates path that is a dangling symlink raises
    nothing and clears nothing, as a session with no gates directory does.

The rollback rows
([execution.md](v3-spike/320-rc2-rollback/execution.md)):

32. **`doctor` names the wrong file for an unreadable document.** It reports
    the failure with the detail "the session's sealed heads do not verify",
    although the file that failed may be a document and the failure a read
    error.

As for rc.1, the candidate is tagged on v3 and not joined to main, so the
plugin marketplace, which reads main, does not offer it. The release flow


Install by temporary name and rename, from the tag, never from the working
tree (R54).

1. After the v3.2.0-rc.2 tag is published, build the tag in a scratch
   worktree:

   ```sh
   git worktree add ~/scratch-v320rc2 v3.2.0-rc.2 && cd ~/scratch-v320rc2 && scripts/build-pi-runtime.sh all
   ```

   The binary is `build/pi/amq-squad`.
2. From the repository, run `up` from the tag build:

   ```sh
   cd ~/code/amq-squad
   ~/scratch-v320rc2/build/pi/amq-squad up --binary ~/scratch-v320rc2/build/pi/amq-squad
   ```

3. Read the lead's first screen and record it in the release evidence
   (RELEASING.md step 6). A dead pane or a `Failed to load extension` line
   means the candidate is not done.
4. Trust the Codex hooks once, if they are not trusted at this path: in one
   Codex seat's pane, run `/hooks` and trust the three
   `/<session-flags>/config.toml` amq-squad activity entries. `amq-squad
   doctor` stops warning when they are trusted.
5. **The lead, right after the restart, when upgrading from 3.1.2.** Every
   task in progress when 3.2 first reads it is stamped with a budget end, and
   the budget end is the later of the grant plus the task's budget (90 minutes for a 3.1.2 row) and the restart plus one lease (ten minutes):
   the budget end is at least one lease after the restart; the lease's own expiry is unchanged, so a seat that is not renewing still ends as lease_expired,
   and the scheduler's tick logs task_budget_warning. Right after the
   restart, the lead has at least one lease in which to extend every
   in-progress task that should keep running
   (`amq-squad task extend ID --by DURATION`). Extending a budget is the
   lead's decision. A later `task extend` raises
   the allowance for the task's next attempt; it does not revive an ended
   one.
