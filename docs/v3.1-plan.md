# amq-squad 3.1 plan, revision 1 (2026-10-30)

Built with amq-squad 3.0.0 itself. The plan of record for 3.0 is
docs/v3-plan.md; its rules (R1 to R52, the amendments, the briefs rulings)
stay in force unless a line here changes one, and every change names the
line it changes. Follow-ups carried into 3.1 are in docs/v3-followups.md.

## 1. Goal, in the owner's words

"We want to copy claude agents team but with more binaries and models, and
experience needs to be seamless. The other main objective is to be able to
work remotely via buzz or grok bot." (2026-10-30)

The interaction model to copy, named by the owner from OpenMuse's README and
taken as a reference only, no dependency: ask for an outcome, follow the
plan, review actions, come back to the result.

## 2. The user story 3.1 ships

1. One binary. In a folder, `amq-squad lead` is a conversation with the
   lead on pi.
2. The owner says what they want. The lead decides whether it works alone
   or needs a team.
3. If it needs a team, its reply is a plan the owner can read: what it will
   do alone, which seats it opens with which binary and model, what each
   seat touches, what the owner will be asked to approve. The plan carries
   the squad.yaml digest. The owner's "yes" is the digest confirmation;
   git init and `amq coop init` run underneath; the team starts.
4. The owner watches and steers from the same conversation. Seats report
   through the lead.
5. The typed actions (tag, release, external send, credential change,
   growth beyond the grant) still stop for the owner's signature over Buzz.
6. The same conversation works from the phone, both ways: the owner
   writes, the lead answers there, progress and results arrive there.

What 3.1 does not do: a Grok bot face (3.2, a second face on the same gate
transport after the signing question is settled); Linux seats (the 3.1
candidate list in follow-ups, not this revision); OpenMuse's engine,
browser container or app.

## 3. Design rulings (reviewer, 2026-10-30), with the lines they change

### 3.1 One lead: the solo lead gains squad tools

- The solo lead gains the tools to propose and start a squad. The operator
  session gains no chat face. The mayor stays what R40 makes it: the fleet
  policy point in the start path (grant, max squads, cost cap fail-closed,
  permitted repositories), called as a library by the lead's start, never
  a second conversational actor.
- Why: R40's "the mayor never answers a gate" is protected by keeping the
  chat partner and the gate path in different processes. The one lead may
  raise a gate and report its state; its tool set never carries a
  gate-answer verb. The seam the owner hit ("I'm solo here") is the solo
  lead's, so the fix belongs where the conversation is.
- **New rule R53 (phase as a tool-list fact).** The one lead has two
  phases: solo (it may edit; it is the owner's single agent) and team
  (after the owner's yes). The switch is enforced by the pi runtime's tool
  list, not by a prompt sentence: on team start the runtime removes the
  edit and write tools from the lead, and its only writes go through the
  task-store verbs. Today the lead-never-edits rule in team mode is a
  role-prompt sentence only (internal/cli/pi_lead.go); a local model will
  not hold a prompt rule across a two-minute turn.
- The owner's yes is the digest confirmation as today: the plan the lead
  prints carries the squad.yaml digest; the yes runs `team apply` with that
  digest. For a root outside the fleet grant, R40's fallback holds: the
  lead proposes, the owner starts. For the dogfood the repository is in
  the grant.

### 3.2 Two-way phone: the core relays the lead's replies

- The fact: the mailbox adapter's reply_timeout is 60 s and a lead turn on
  the local model took about two minutes, so the lead's answer can never be
  the inbound's one non-status reply. Two-way needs an outbound post
  independent of any inbound.
- Ruling: the lead never holds a key. The lead's answers, progress and
  results are AMQ replies on the cockpit thread from the attach handle; the
  core (the attachment, which holds the body key for the question post
  under ruling 20 point 1 and R33) relays them to the DM.
- **R33 widened by one purpose, "lead reply relay"**: text only, through
  redact.Block, rate-bounded (one progress post per state change or per N
  minutes; every answer and every result), the key in the core's process
  only. The relay refuses to carry anything shaped like a gate answer or a
  typed approval; gate lines come only from the owner's signed DM through
  gateverify (R40). Inbound stays as today: the handler's one non-status
  reply becomes `accepted <request id>` at once; the answer arrives later
  as a relay post.
- The purpose retires with the body key when amq-remote offers a post
  surface on serve's connection. Upstream ask 19, filed at the start of
  brief 2 on the owner's go: "conversation mode on the mailbox adapter:
  every bodied reply on the thread posts until a final reply or the
  timeout".
- The chat partner is the lead (3.1), not the mayor.
- Owner decision 1 (pending): A, widen R33 now and retire later (two-way in
  3.1); B, wait for the upstream surface and ship 3.1 one-way plus
  `accepted` and the final result. Recommended: A.

### 3.3 The dogfood: 3.1 is built by a 3.0 squad on this repository

- Catalog first. The registry builder iterates the catalog's codex models
  only (internal/registry/build.go) and the catalog names gpt-5.6-sol and
  gpt-5.6-terra only (internal/agentcatalog/catalog.go), so a GPT-6 id in
  ~/.codex/config.toml gets no registry row and doctor cannot probe it.
  Step 0 adds the GPT-6 family to the catalog with tiers, then `doctor
  --probe` against the installed codex-cli (ProbeCodexModel) is the proof
  per id; the 5.6 entries stay. The probe answers usable, never tier.
  Owner decision 2 (pending): A, mirror the 5.6 mapping (GPT-6.1 Sol and
  GPT-6 Sol frontier with planning, implementation, review, security;
  GPT-6.1 Terra balanced, implementation; GPT-6 Astra and GPT-6 Luna
  balanced, implementation, until a probe or the owner says otherwise); B,
  the owner writes the tiers. Recommended: A. The dogfood seats use only
  ids the probe passed.
- Repository: `amq coop init` (done 2026-10-30), a merge grant on v3 (the
  owner's grants file), a CI-only ruleset on v3 for the train
  (owner-present).
- **New rule R54 (no self-hosting from the working tree).** The squad runs
  the installed tagged binary from PATH (3.0.0 today) and never a binary
  built from the branch it edits. A newer binary enters only after the
  train merges it and the owner installs it by temp name and rename.
- The lead for brief 1: seats only, with the planning session and the task
  store as the lead. The pi lead on a local 27b model cannot be trusted
  with brief 1's own build (the "I'm solo here" turn and the two-minute
  turns are what briefs 1 and 3 fix). Handoff criterion, measured: the pi
  lead on a cloud entry opens a team from a conversation on this
  repository (brief 1's acceptance run); then it leads brief 2.

## 5. Acceptance of 3.1 (the rows the tag waits on)

1. From a conversation in a folder with no git, the lead proposes a team,
   the owner says yes once, the team starts (brief 1; the acceptance run on
   this repository is also the handoff criterion).
2. In team phase the lead has no edit or write tool (R53), proven by a
   row that fails when the tool list is not narrowed.
3. From the phone: a question, the `accepted` receipt within the adapter's
   timeout, the lead's answer as a relay post, a progress post on a state
   change, the result post; a gate-shaped line in the relay refused
   (brief 2).
4. The pi lead on a cloud entry (brief 1) leads brief 2's build.
5. The dogfood record: every 3.1 PR produced by the harness commit step and
   merged by the train (3-2 acceptance 4 as re-scoped), on the tagged
   binary (R54).
