# v2.28 "Simple Mode": remove the ceremony layer

**Status:** proposed — reviewed by Codex 2026-08-03 (verdict ACCEPT-WITH-NITS), then simplified further by operator decision: no prepare/go split, no goal step in launch, no bootstrap ack, no custom roots, pruned CLI surface.
**Motivation:** #643, #644, #645 (and #598, #618 before them) — the launch failures investigated across recent releases trace to the verification layer, not the coordination layer it guards. The prepared-launch integrity system verifies amq-squad's own output against amq-squad's own output; in the incidents on record it caught no real defect while producing deterministic, unrecoverable launch failures. (The prepared system persisted only the *digest* of the accepted bootstrap and discarded the prompt itself — `bootstrap_drift_evidence_598.go:13` — so spawn-time re-rendering was forced by design.)

**Design bar:** Claude Code agent teams. The brief travels with the spawn — no gap, so no drift detection, digests, tokens, readiness rows, or receipts. Messages are confirmed by transport acceptance. Tasks are a flat shared list with plain status fields. The only gates are human approval and checks against external reality (CI, review state).

**Governing rule** (to be added to `.amq-squad/team-rules.md`):
> Persist authoritative inputs, coordination state, and observations of external systems. Never persist a second owned representation whose sole purpose is to certify another owned representation. Any recovery command the CLI prints must be exercised end-to-end in CI. A bug closed without a class-level test is not closed.

**Core invariant (all five issues):** the tool re-derives state it already persisted, then trusts the derivation over the record — spawn re-renders the bootstrap instead of reading prepared bytes (#643), recovery re-computes readiness across a state boundary (#644), status re-resolves the AMQ root from cwd instead of reading `launch.json` (#645). The v2.28 rule:

> A **selected, valid** launch record is authoritative for launch coordinates and captured invocation facts — root, team home, cwd, actor identity, PID, TTY, pane, binary, argv. Current runtime state is determined by **probing those recorded coordinates** (PID alive? pane alive?), never assumed from the record and never re-derived from configuration.

Conflict semantics (never silent): one matching live record → select it; multiple → `duplicate_live`, no winner election; dead PID/pane → `stopped`; no record → labeled `unmanaged`; inconsistent record → `record_invalid`. A live process with changed config is `live / config-diverged`, never `missing`.

## The whole CLI (pruned surface)

```
amq-squad start      # shows roster + briefs (+ optional goal) → y/N (--yes for automation) → agents up. That's launch.
amq-squad status     # reads launch.json, probes PIDs/panes. Truth.
amq-squad send       # message an agent. exit 0 = accepted.
amq-squad task       # add | claim | done | list
amq-squad goal       # hand the lead a goal any time; also offered as an optional step inside `start`
amq-squad gate       # raise | close — review holds
amq-squad verify     # merge — real CI + real review evidence
amq-squad down       # stop the squad
amq-squad doctor     # diagnose (same record-first pipeline as status)
```

Everything not on this list is deleted or folded in. One canonical AMQ root per project/profile/session — custom roots are removed as a feature.

## Launch flow

One command, one question:

1. `start` resolves project/profile/session (path canonicalized once: `EvalSymlinks` + on-disk case). Builds roster, argv, per-role brief bytes in memory. Runs spawn preflight (binary exists, valid model/trust, managed tmux).
2. Shows the plan. One default-No approval (`--yes` skips for automation).
3. Under the session launch lock: writes briefs to disk once, creates/adopts the canonical namespace, spawns each agent whose instruction is "read `.amq-squad/team-rules.md` and your brief at `<absolute path>`", writes each launch record.
4. Verifies each pane owns a live process before reporting success — the CLI never prints "started" for a dead pane (the #643 lesson: agents died instantly and the launcher reported success).
5. Interrupted launch → run `start` again; live roles are kept, dead ones respawned, it rolls forward. Nothing to reconcile because nothing was derived.

**Goal is an optional wizard step.** The `start` wizard asks "Goal for the lead? (optional — Enter to skip)". If the operator types one, it is shown as part of the plan they approve, and sent to the lead as an ordinary message **after** all agents are verified live — the last act of a successful launch, never a precondition of it. If they skip, they can assign one any time later with `goal` (or plain `send` to the lead). Either way goal delivery is a single human-initiated send: no dedup machinery, no delivery states, no supervision gates. A rolled-forward rerun of `start` does not re-send a goal; assigning after recovery is the operator's call.

**No bootstrap ack.** Agents read the team rules and their brief; their work shows whether they did. No expectation state machine, no ack gates anywhere.

## Roster changes mid-run (free by design)

Launch is a reconciler: desired roster vs. live launch records. Therefore, on a running team:
- **Add:** add the role to the roster, run `start` — the wizard shows only the delta ("adding: <role>") for approval and spawns just the missing agent. Running agents are untouched.
- **Remove:** `down <role>` — kill the recorded pane/PID, archive the record.
- **Replace:** `down <role>` then `start`.

Same mechanism as crash recovery — no separate roster-edit machinery, no manifest to invalidate (the #604 problem class is gone with the hashes).

## Status/liveness (from #645)

`status` and `doctor` (and `down`) follow one pipeline: read launch records from the canonical root → select or report conflicts → probe the recorded PID/pane. Recordless tmux discovery runs only when no record exists and is labeled `unmanaged`. A stale worktree-local `.agent-mail` remnant is informational, never grounds for `missing`.

## Seamlessness bar (what "like Claude agent teams" means, measurably)

Claude teams feel seamless because the harness guarantees three things. v2.28 must match them:

1. **Wake reliability is a launch feature, not a subsystem — and amq-squad owns it.** Wake must not depend on upstream amq wake support or on agents remembering to poll. `start` spawns one **session notifier** per session: it watches the canonical root's inboxes and, on a new message for role X, nudges X's pane looked up from `launch.json` (record-first). Sending *is* waking — the lead wakes a worker just by `send`ing. Only dependency: tmux `send-keys`, which is already load-bearing for spawn. A message sent to an idle agent produces a response with **zero human keystrokes**. The 2.27 wake-loss bug class ("idle agents go deaf") is a release blocker.
2. **Time-to-working-team is measured and protected:** `start` with 4 codex actors → all live with briefs read in under ~30s on a warm machine. Regressions here are treated like correctness bugs.
3. **Resume restores the mind, not just the process.** Restoring an exited agent reattaches its recorded conversation (`codex resume <conversation-id>` from launch.json), so the agent continues with its accumulated context. A restore that spawns a blank agent is a failed restore.

## Acceptance criteria

1. Fresh project, no AMQ root, project path spelled with wrong case on APFS: `start` → y → all agents live, first try (#643).
2. Kill the launcher after namespace creation but before all agents spawn; run `start` again → converges to all-live without deleting anything (#644).
3. Isolated-worktree actor with stale worktree-local remnant + live canonical record → `status`, `doctor`, and `down --dry-run` all report the same live actor and canonical root (#645).
4. Two genuinely live matching records → explicit `duplicate_live`; neither silently elected.
5. Two concurrent `start` invocations → one squad, no duplicate workers.
6. Child exits immediately (bad argv / missing brief) → precise per-role failure; rerun converges.
7. `send` between agents → delivered; no receipt artifacts anywhere in `.amq-squad/`.
8. `task add` → `task claim` → `task done`; nothing blocks; two concurrent claimers → exactly one wins.
9. Goal typed in the wizard → delivered to the lead only after all agents verify live; wizard skipped goal + later `goal` command → lead receives it. A rerun of `start` never re-sends a goal.
10. `grep -r "sha256\|drift\|generation token\|readiness" internal/cli` → no launch-path hits.
11. A dead-ended v2.27 namespace recovers without manual deletion.
12. On a running 3-agent team: add a role to the roster, run `start` → exactly one new agent spawns, the three live ones untouched; `down <role>` → exactly that agent stops.
13. `send` to an agent that has been idle for 10+ minutes → it acts on the message with no human keystroke in its pane.
14. Restore of an exited agent resumes its recorded conversation; the restored agent demonstrably retains pre-exit context.

## Sequencing (each step ships green on main)

1. Class-level tests for #643/#644/#645 + crash injection (after namespace creation, pane creation, child dispatch, record write) + concurrent `start`.
2. Build the simple launcher vertically (reuse namespace resolution, preflight, launch records, tmux control, liveness, wake, worktree checks).
3. Switch `start` and delete the wizard/prepared production path (keep a legacy reader long enough to recover v2.27 sessions).
4. Rewire consumers (compound release off receipts; goal/gate/task).
5. Delete the old machinery.
6. Prune the task schema and CLI surface last, so regressions stay attributable.
