# amq-squad v3.3.0

These are the notes for 3.3.0, built from the tip of `release/v3.3` after
#1025 (`312a27d3eeb5652d126c59768e3d60426413132b`, the v3.3.0-rc.1 tag's
commit). The module path is unchanged:

```sh
go install github.com/omriariav/amq-squad/v3/cmd/amq-squad@v3.3.0
```

A `go install` build carries no embedded pi runtime. The binary the squad runs
is built from the tag by `scripts/build-pi-runtime.sh`, as the owner steps
below show. The earlier notes are
[docs/v3.2.0-release-notes.md](v3.2.0-release-notes.md) and the notes it links.
The rc.1 form of these notes is this file at the `v3.3.0-rc.1` tag; the rc.1
soak's record is
[docs/v3-spike/5-release-evidence/release-v3.3.0-rc.1/](v3-spike/5-release-evidence/release-v3.3.0-rc.1/README.md).

## What 3.3 is

Answering the squad from your phone works the same way more often, and the
squad's task records say more about themselves:

- An answer that comes after a gate's time ran out gets the question asked
  again, in its thread, once.
- Every Buzz reply to an answer says what was recorded.
- The lead's screen tells you to answer on the phone.
- Each task row says which moves are open next.
- The AMQ floor is 0.140.0.

## Your answer's reply names the decision (#1006)

When your answer to a gate is verified and committed, the Buzz reply now reads
`accepted <gate> <class> approved` or `accepted <gate> <class> denied`: the
decision as the squad recorded it, not only that the answer was taken. The
other replies are unchanged (the table in
[docs/v3-buzz/README.md](v3-buzz/README.md)).

## A late answer gets the question asked again (#1012, #1016, #1018, #1022)

If you answer a gate in its thread after its time ran out, the answer does not
approve anything. The question is asked again as a reply in the gate's thread,
with a new window, once; a later answer in the gate's thread, dated after that
message, is what counts. An answer outside the gate's thread gets the thread
refusal instead (`not_in_gate_thread` or `wrong_gate_thread`):

- The reply to your late answer is `refused <gate> gate_lapsed` and
  `re-ask: answer in the gate thread (event <id>)`.
- An answer dated before the question was asked again, or in the same second,
  is refused `answered_before_reask`: answer again in the thread. The late
  answer that caused the re-ask never counts.
- The new window's length is stated exactly (whole hours, or minutes and
  seconds), never rounded up.
- If posting the asked-again question fails, the reply is
  `refused <gate> reask_publish_failed`. The same question is posted when that
  answer is delivered again or when you send the next answer for the gate.
- The lead's screen and pi count such a gate as open until its new window ends.

The full rule, sentence by sentence, is
[docs/v3-spike/330-a1-3-window/README.md](v3-spike/330-a1-3-window/README.md).

## The words a bare answer can be (#997)

A bare answer is one of eleven words, standing alone: `yes`, `approve`, `y`,
`ok`, `go ahead`, `כן`, `no`, `deny`, `n`, `stop`, `לא`. A typed answer is
exactly `approve|deny <gate-id> <class> <prefix>`. The relay refuses to carry a
lead reply any line of which is, as a whole, answer-shaped: one of those words
alone or with a gate id or the typed tuple's parts (README, "What the relay
never carries"). Who may
answer a gate, per channel, is
[docs/v3-spike/330-a0-sender-auth/README.md](v3-spike/330-a0-sender-auth/README.md)
(#967, #968).

## The lead's screen says to answer on the phone (#1009, #1011)

While the squad waits on you, the screen's waiting header reads
`waiting on you (N): answer on the phone; /answer shows it`, once. Every open
question is named in plain words, also one whose question cannot be shown. A
gate action the screen does not know reads as the generic words.

## Each task says which moves are open next (#1020, #1023, #970-#1015)

`task show --json` carries `data.next` beside the task, and each task row of
`status --json` carries `next`: the moves open from the task's state, each
with its command, who runs it (`lead`, `holder` or `owner`) and what may still
refuse it. `status --json` lists every role's moves. `task show --json` with
`--me` (or AM_ME) lists only the moves of the roles that handle holds (holder,
or lead by its own launch record), and `[]` for a handle that holds neither;
without a handle it lists every role's. It is derived from the task machine's declaration and the task
record; the stored task file is unchanged. `next` lists the moves for the lead,
holder and owner roles; a handle holding none of them may still run moves it
doesn't list (a non-lead creator's reset; a pending task's block and cancel; a
leased task's release).

status --json task rows gain next (additive, schema 1). Consumers that decode
without refusing unknown fields are unaffected; amq-noc's vendored status
golden and its sha need a re-vendor.

The task machine behind it is declared once, with its states, moves, outcomes
and block group, and its reasons are on one state contract that the code and pi
both check (#970, #971, #976, #980, #988, #992, #993, #1010, #1013, #1015,
#1019, #1022). The values written are the same strings as in 3.2.0. Two
reasons gain words on the lead's screen (#1013): a task waiting or blocked
because its seat's process exited reads "the seat's process exited while it
held the task", and a task blocked because a tool has no pinned path reads
"the tool has no pinned path and digest", with "ask the owner to pin the
tool's path and digest in registry.yaml".

## A seat or `--me` handle is checked before any path is built from it (#1020, #1021)

Task verbs now refuse a --me or AM_ME that is not a valid handle
(`team.ValidateHandle`); every handle a v3 squad can hold passes it. `pi run`
and `amq-squad lead` refuse a seat handle that could leave the seat's
directory before they build the agent directory, the resume ledger's path or
the temporary directory from it.

## AMQ 0.140.0 is the floor (#972, #975, #977, #969)

The AMQ module pin moved from v0.116.2 to v0.140.0, and `amq-squad doctor`
refuses an installed `amq`, `amq-remote` or `amq-owner-sign` below 0.140.0. The
session inspect floor, code that no command reached, is removed (#969).

## The merge train lands a PR whose compare has no patch for a file (#1000, #1002)

When GitHub's compare returns no `patch` for a file, the train no longer
refuses the update for that alone. It checks the compare's file list against a
separately requested diff from GitHub's API (the same files, each file's
additions and deletions, the diff's structure) and takes the patch-id of that
diff with `git patch-id --stable`. An incomplete or inconsistent response is
still refused.

## 3.2.0's Known limit 35, narrowed (#995)

A seat whose task branch was cut from a tip later than its launch base, and
whose attempt ended with no commit, is no longer refused at its next prepare
with `seat_head_detached_unmerged` when its head is the lease base fetched at
the grant, or an ancestor of it. The refusal stays when the lease base is
missing or unreadable, and for a head only a newer remote tip holds: the clean
makes no network call
([docs/v3-spike/32x-seat-head-remote/README.md](v3-spike/32x-seat-head-remote/README.md),
"What it does not cover"). #982 and #983 add tests and a note for the legacy
gate count the screen already shows beside a gate alert; the screen is
unchanged.

## Upgrading from 3.2.0

Install 3.3.0 with `up --binary`, as the owner and lead steps below show.
Nothing migrates. No sealed layout and no schema version changed between 3.2.0
and this release: the commit and exits ledgers, the task store, the gate store's
records and answers, the launch records and the status document keep their
3.2.0 versions. The one new thing on disk is the gate store's `windows/`
directory, written when a gate is asked again after its window. `next` is
output of `status --json` and `task show --json`, never stored. If `amq-squad
doctor` says `~/.amq-squad/registry.yaml` is out of date, run `amq-squad doctor
--write-registry` to write it at the new AMQ pin, v0.140.0.

One stored approval stops verifying after the upgrade: a bare answer stored
under 3.2.0 with two or more trailing punctuation marks (`yes!!!`). 3.3.0 reads a
bare answer with at most one mark, so the merge train, the release flow, verify
action and growth refuse that approval. `gate status` still shows it accepted,
and the guard still admits the action and target it approved.

### From 3.3.0-rc.1

The binary swap only. Nothing migrates: no Go file differs between the
`v3.3.0-rc.1` tag and 3.3.0 except the plugin version a test expects
(`internal/claudeseat/relprep_version_test.go`); the rest of the change is the
version bump and documentation.

## Rolling back

Roll back with `up --binary` and the 3.2.0 binary, the one kept before the
install on a host coming from 3.2.0 (step 2 below). 3.2.0 reads everything 3.3.0 wrote. Two kinds of gate read
differently: a gate asked again after its window (3.2.0 does not read the
`windows/` directory), and a gate approved with a bare word 3.3.0 added (`y`,
`ok`, `go ahead`, `כן`), which 3.2.0's parser does not know.

- An unanswered gate that was asked again after its window shows as expired.
- 3.2.0's hook guard admits an action whose approval was given through an
  asked-again question or in one of those four words, while 3.2.0's merge
  train, release flow, verify action and growth check refuse the same approval:
  each re-verifies the stored answer and refuses it. `gate status` and the
  lead's screen show it accepted. Use or settle such approvals before rolling
  back (known limits 5 and 6).
- Under 3.2.0 the merge train, the release flow and a growth check do not ask a
  gate again: each reuses its gate's id (a merge gate's is fixed by the PR's head
  and rules, a release gate's by its attempt, a growth gate's by its task and
  target), and a second raise of an id is refused. A new merge head, a new
  release attempt or a new target raises a new gate; `amq-squad gate raise` with
  a new id asks again for the same target.
- `amq-squad uninstall --write` run by the 3.2.0 binary removes `windows/` with
  the session state and keeps the rest of the gate store. Back on 3.3.0, a gate
  that was asked again after its window and is unanswered shows expired. An
  approval given through the asked-again question still shows accepted, and the
  guard still admits its action and target, but the merge train, the release
  flow, verify action and growth refuse it. Other approvals are unaffected.
- A `~/.amq-squad/registry.yaml` written by 3.3.0's doctor reads under 3.2.0
  with an "out of date" warning; `amq-squad doctor --write-registry` writes it
  at 3.2.0's pin.

## Known limits

1. A gate re-asked because its thread history changed can still be approved by
   the owner's original answer if the relay delivers it again before any other
   answer (3.2.0 behaviour; fixed in 3.3.x).
2. A Buzz request can occasionally be refused native_error 'its delivery never
   started' by a race in amq-remote's admission and reconcile (upstream, every
   AMQ version through v0.149.1); send it again; the gate and its answer are
   unaffected.
3. `task claim --json` prints the task's `updated_at` from before the claim; the
   stored task and every other reader carry the claim's time (fixed in 3.3.x).
4. If posting the asked-again question fails and no later answer for that gate
   arrives, the question stays open on the lead's screen without reaching the
   phone; reply in the gate's thread to post it. It shows open until the
   asked-again window ends, then expired; a later answer posts the same question
   and does not extend that window.
5. After a rollback, 3.2.0's hook guard admits an action whose approval was
   given through an asked-again question, while 3.2.0's merge train, release
   flow, verify action and growth check refuse the same approval (they re-verify
   it against the original window). `gate status` and the lead's screen show it
   accepted. Use or settle such approvals before rolling back.
6. After a rollback, 3.2.0's hook guard admits an action whose approval was
   given in an answer word 3.3.0 added (`y`, `ok`, `go ahead`, `כן`), while
   3.2.0's merge train, release flow, verify action and growth check refuse the
   same approval (3.2.0's parser does not know the word). `gate status` and the
   lead's screen show it accepted. Use or settle such approvals before rolling
   back.
7. A gate raised as the first write into a new session cannot be answered (no_squad_identity); make sure the session root exists first, for example by starting the session's attach before release prepare or gate raise.

## Evidence

GitHub CI skips internal/buzz's owner dry-run tests: the real-AMQ lane installs
`amq` alone and runs other packages, and those tests skip without
`amq-remote` and `amq-owner-sign`. The local soak's tally of `native_error` /
"its delivery never started" is the only evidence for them.

## Owner and lead steps for 3.3.0

3.3.0 is the release, not a candidate. It is tagged on the `release/v3.3`
branch and published as the latest release, not as a prerelease, so no step
here marks it. After the lead's first screen on the 3.3.0 build is recorded
(step 4), the lead joins the v3.3.0 tag into main. The plugin marketplace
reads main, so that join is the step that offers 3.3.0 to plugin users.

Install by temporary name and rename, from the tag, never from the working
tree (R54).

1. After the v3.3.0 tag is published, build the tag in a scratch
   worktree:

   ```sh
   git worktree add ~/scratch-v330-build v3.3.0 && cd ~/scratch-v330-build && scripts/build-pi-runtime.sh all
   ```

   The binary is `build/pi/amq-squad`.
2. Keep a copy of the installed binary first, so a rollback has it:

   ```sh
   mkdir -p ~/amq-squad-backup && cp -p ~/go/bin/amq-squad ~/amq-squad-backup/ && shasum -a 256 ~/amq-squad-backup/amq-squad
   ```
3. From the repository, run `up` from the tag build:

   ```sh
   cd ~/code/amq-squad
   ~/scratch-v330-build/build/pi/amq-squad up --binary ~/scratch-v330-build/build/pi/amq-squad
   ```

   If the squad's lead is running, quit it first: `up` installs the binary
   and then refuses `lead_running`, because it never stops a lead whose tmux
   pane exists.
4. Read the lead's first screen and record it in the release evidence
   (RELEASING.md step 6). A dead pane or a `Failed to load extension` line
   means the release is not done.
